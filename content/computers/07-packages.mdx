## Nobody starts from scratch

Need to read dates, talk to a database, or build web pages? Someone has almost certainly written that code already and published it as a **package**. A **package manager** downloads packages, and the packages they depend on, for you.

| Language | Package manager | Where packages come from | The project's list |
| --- | --- | --- | --- |
| JavaScript | **npm** | the npm registry | `package.json` |
| Python | **pip** | PyPI | `requirements.txt` or `pyproject.toml` |

## What happens when you install

When Groundwork's `start.bat` ran `npm ci` the first time, npm:

1. Read `package.json` to see what Groundwork needs.
2. Read `package-lock.json` to get the exact versions.
3. Downloaded every package, plus every package *those* need, a few hundred in total.
4. Put them all in a folder called `node_modules`.

That's why the first start needed the internet, and later starts don't: everything is already in `node_modules`.

## Version numbers

Most packages use **semantic versioning**: `major.minor.patch`, like `19.2.1`.

- **Patch** (19.2.**1**): bug fixes.
- **Minor** (19.**2**.0): new features, nothing broken.
- **Major** (**19**.0.0): something may work differently, so upgrading may need changes.

In `package.json`, `"^19.0.0"` means "19.0.0 or any newer 19.x". That flexibility is useful, but it means two installs months apart can get different versions.

## Lockfiles

A **lockfile** (`package-lock.json` for npm) records the **exact** version of every installed package, including the hidden ones. Commit it to Git, and everyone, including the live server, gets identical installs with `npm ci`.

| File | Commit it to Git? |
| --- | --- |
| `package.json` | Yes |
| `package-lock.json` | Yes |
| `node_modules` | **No.** It's huge and can be rebuilt. |

## Trusting strangers' code

Every package runs with the same access as your own code. It can read your files and environment variables, and reach the internet. Most packages are written in good faith, but attackers do publish harmful ones, and occasionally break into real ones.

Sensible habits:

- **Check the exact name.** Typos are how typosquatting works.
- **Look at its track record:** downloads, publisher, last update.
- **Prefer fewer, well-known packages.** Every package is something you're trusting.
- **Run `npm audit`** now and then. It checks your packages against a list of known security problems.

<ConsultantNote>
Auditing a client's dependencies is a real, billable piece of work: how many packages, how out of date, any known vulnerabilities, any abandoned ones. Old, unmaintained dependencies are behind a huge number of real security breaches.
</ConsultantNote>
