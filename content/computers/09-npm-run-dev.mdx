## It's just a shortcut

In the last lesson you saw that `package.json` can have a `"scripts"` section. Here's a typical one:

```json
"scripts": {
  "dev": "vite",
  "build": "vite build",
  "test": "vitest"
}
```

It's a JSON object. Each name on the left is a short nickname, and the text on the right is the real command it stands for. These are **npm scripts**.

When you type `npm run dev`, npm does exactly this:

1. Opens the `package.json` in the current folder.
2. Looks in `"scripts"` for the name `dev`.
3. Runs the command it finds there: in this case, `vite`.

That's it. The names are just conventions that most projects follow, not magic words. If a project's instructions (usually in a file called `README.md`) say `npm run dev` and you get this:

```text
npm error Missing script: "dev"
```

it means there's no script called `dev` in that package.json. Open package.json and look at which scripts really exist. Maybe it's called `start` or `serve`.

npm does one extra helpful thing: when it runs a script, it lets the command use programs from the project's own `node_modules`. That's how `vite` runs even though you never installed Vite on its own. It's one of the project's devDependencies, sitting in node_modules.

<details>
<summary>Quick check: a README says `npm run serve`. Where would you look to see what that actually runs?</summary>

In the project's package.json, in the `"scripts"` section, next to the name `serve`.
</details>

## The usual routine

For almost any JavaScript project you download:

```text
npm install      ← once, to download the packages into node_modules
npm run dev      ← every time you want to work on it
```

Remember from *Packages*: `node_modules` isn't shared along with the code, because it's huge and can be rebuilt. So when you download a project, you get its package.json and lockfile, but **no packages**. If you skip `npm install` and go straight to `npm run dev`, you'll get errors saying packages or commands can't be found.

(If the project has a `package-lock.json`, `npm ci` is even better than `npm install`, because it installs exactly the locked versions.)

## What a dev server does

Most `dev` scripts start a **development server**, or **dev server**. It's a server program, like Groundwork's, running on your own computer, that serves the website you're working on at an address like:

```text
http://localhost:5173
```

You know how to read that now: `localhost` means this computer, and `5173` is the port the dev server is listening on. You open that address in your browser to see the site.

While it runs, a dev server:

- **Watches the project's files** for changes.
- **Updates the browser the moment you save a change.** Edit some text, press save, and the page in your browser changes by itself a second later. This is called **hot reload**.
- **Shows detailed error messages**, meant for developers, when something's wrong.

A popular tool for this is **Vite** (said "veet", French for "quick"). When a package.json says `"dev": "vite"`, Vite is the dev server.

### Why the terminal has to stay open

A dev server is a process, like any other. It runs **inside the terminal window you started it from**. While it's running, that window is busy: it shows the server's messages, and you can't type new commands into it.

- **Close that terminal**, and the process ends. The dev server stops, and the browser can't reach it any more.
- **Ctrl+C** in that terminal stops it cleanly.
- To type other commands while it runs, **open a second terminal window**. You'll do exactly that in the task.

This is the same reason you keep the black Groundwork window open: it's Groundwork's server process.

<details>
<summary>Quick check: you start a dev server, then close the terminal window. What happens to the website at localhost:5173?</summary>

It stops working. The dev server was a process running in that window, so closing the window ended it, and nothing is listening on port 5173 any more.
</details>

## Dev and build

The dev server is for **working on** a website. It's not how a website is published for real visitors.

To publish a website, you run a **build**: usually `npm run build`. A build takes all the project's source code and produces a folder of finished, optimized files, ready to be put on a real server. That folder is usually called `dist` (short for distribution) or `build`. No dev server is involved: the build runs, writes the files, and finishes.

| | `npm run dev` | `npm run build` |
| --- | --- | --- |
| What it's for | Working on the code | Making files to publish |
| What you get | A server running on localhost | A folder, often `dist`, of finished files |
| When you change code | The browser updates by itself | You run the build again |
| Error messages | Detailed, for developers | Hidden from visitors |
| Does it keep running? | Yes, until you stop it | No, it finishes |

Groundwork works the same way. On its first start, `start.bat` ran a build into a `dist` folder. Then it started a small server that hands those finished files to your browser.

## Frontend and backend

You'll often hear that a project has two halves:

- The **frontend** is the part that runs **in the browser**: the pages, buttons and everything you see and click.
- The **backend** is the part that runs **on a server**: it stores data, checks passwords, talks to other services, and answers the frontend's requests.

Many projects have a dev server for each half, on different ports: for example, Vite serving the frontend on port 5173, and a backend server on port 3000. Groundwork is like this. When developers work on Groundwork itself, its `npm run dev` starts both.

## Your own tiny server

In the task, you'll write a server in one line of JavaScript. You're not expected to write code like this yet. But you can read it, piece by piece:

```javascript
require("http")
  .createServer((req, res) => res.end("Hello from my own server"))
  .listen(4399, "127.0.0.1", () => console.log("Listening on http://localhost:4399"))
```

| Piece | In plain words |
| --- | --- |
| `require("http")` | "Get Node's built-in tools for web servers." |
| `.createServer(...)` | "Make a server." |
| `(req, res) => res.end("Hello...")` | "For every request (`req`) that arrives, send back a response (`res`) saying Hello from my own server." |
| `.listen(4399, "127.0.0.1", ...)` | "Start listening on port 4399, for this computer only." |
| `() => console.log("Listening...")` | "Once it's listening, print a message." |

You'll also use two new commands:

- **`npm.cmd init -y`** creates a new, empty `package.json` in the current folder. `init` means start a new project, and `-y` means "yes to all the default answers".
- **`npm.cmd pkg set scripts.dev="node server.js"`** adds a script called `dev` to package.json without you editing the file by hand.

And to talk to your server from a second window:

- **curl** is a program, included with Windows, that sends a request to a web address and shows (or saves) the response. It's like a browser with no window. In PowerShell, type `curl.exe`, because plain `curl` means something different there. You'll use curl much more in Stage 2.

<ConsultantNote>
"Can you get this project running?" is a common first task with a new client. You now know the checklist: the right Node version, install the packages (`npm ci` or `npm install`), check which scripts package.json has, set any environment variables the project needs (often from a `.env` file), then `npm run dev`. When it fails, the error usually points at one of those steps.
</ConsultantNote>
