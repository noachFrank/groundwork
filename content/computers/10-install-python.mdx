## In this lesson

- Install a real programming language, Python, yourself.
- Avoid the two traps that catch almost everyone on Windows.
- Make a **virtual environment**, the way professionals keep each project's packages separate.

This lesson needs the internet for the download. After that, Python works offline.

## Installing things is part of the job

Groundwork's Python lessons run Python for you, inside the app. But real projects need Python installed on the computer itself, so you can run `.py` scripts from the terminal like you ran `.js` scripts with Node.

Installing tools, and fixing installs that went wrong, is a skill you'll use constantly, for yourself and for clients. Everything in this lesson builds on the PATH lesson, so it's worth a quick look back if "not recognized" doesn't immediately make you think "PATH".

## The two traps

Almost every "Python doesn't work" problem on Windows is one of these.

### 1. The PATH box

The installer from python.org has a checkbox at the bottom of its first screen: **Add python.exe to PATH**. It's **not ticked** by default.

Without it, Python is installed perfectly well, but typing `python` gives "not recognized", because Python's folder isn't in PATH, so Windows doesn't know where to look. Tick it before you click Install.

And after installing, **open a new terminal**. Any terminal that was already open still has the old PATH.

### 2. The Microsoft Store alias

Windows comes with a fake `python` command, called an **app execution alias**, that just opens the Microsoft Store page for Python. If the real Python isn't on PATH, you get the Store instead of Python, which is confusing, because a `python` command clearly *exists*.

You can switch these aliases off in **Settings → Apps → Advanced app settings → App execution aliases**: turn off the two that say python.

Python on Windows also installs **`py`**, a launcher that finds whichever versions of Python you have, wherever they are. If `python` misbehaves, `py --version` is a good fallback.

## Running a module with -m

You'll see `python -m` a lot. Python comes with many built-in tools, called **modules**. `-m` means "run this built-in module". So:

- `python -m venv .venv` runs the `venv` tool, which makes virtual environments.
- `python -m pip install requests` runs pip, the package manager, through this exact Python.

Using `python -m pip` instead of plain `pip` guarantees the package is installed for the Python you meant, which matters when a computer has more than one.

## Virtual environments

Imagine two projects on one laptop: one needs version 1 of a package, and the other needs version 2. If packages were installed for the whole computer, they'd fight, and one project would break.

A **virtual environment** solves this. It's a folder, usually called `.venv`, inside a project, with its own private copy of Python and its own private set of packages. Install a package into one project's `.venv`, and other projects never see it.

```powershell
python -m venv .venv                                # make it
.\.venv\Scripts\python.exe -m pip install requests  # install a package into it
.\.venv\Scripts\python.exe my-script.py             # run a script with it
```

The path `.\.venv\Scripts\python.exe` means "the Python inside this project's .venv folder". Using it directly is the simplest way to be sure you're working inside the virtual environment.

You'll often see instructions say to **activate** the environment first, with `.venv\Scripts\Activate.ps1`. Activating just puts the `.venv` folder at the front of PATH for that terminal. It's a `.ps1` file, though, so the execution policy may block it. Running `.venv\Scripts\python.exe` directly does the same job without activating.

## Recording what's installed

`pip freeze` lists every package installed in the environment, with exact versions. Redirect it into a file and you've got the traditional `requirements.txt`:

```powershell
.\.venv\Scripts\python.exe -m pip freeze > requirements.txt
```

Anyone else can then recreate the same set of packages with `pip install -r requirements.txt`.

### Python and JavaScript, side by side

| Python | JavaScript |
| --- | --- |
| `pip` | `npm` |
| `.venv` folder | `node_modules` folder |
| `requirements.txt` | `package.json` and its lockfile |

As with node_modules, the `.venv` folder is never shared along with the code: it's big, and it can be rebuilt. The `requirements.txt` file is shared.

<ConsultantNote>
Clear setup instructions are a gift. When you hand a project to a client, include exactly which version of Python or Node to install, which boxes to tick, and the commands to run, in order. Most "it doesn't work" calls after a handover come from a missing setup step.
</ConsultantNote>
