## Nobody starts from scratch

Suppose you're building a website for a shop, and it needs to show dates nicely, send emails, and talk to a payment company. You could write all of that yourself. It would take months, and it would have bugs that other people already found and fixed years ago.

Instead, programmers reuse code that other people have written and published. In *When AI is confidently wrong* you met the idea of a **package**: a bundle of code someone has published so others can reuse it. Now for the details.

A package usually does one job well: handling dates, sending email, drawing charts, building web pages. When your project uses a package, that package is a **dependency** of your project: your project depends on it to work.

### Dependencies have dependencies

Packages are written by programmers too, so they use other packages. Those use others, and so on. These hidden, second-hand dependencies are called **transitive dependencies**.

So a project that lists 15 packages it needs might actually install several hundred. Groundwork lists about 30, and installing it downloads a few hundred. Every one of them is code written by someone else, running on your computer.

<details>
<summary>Quick check: your project uses package A, and package A uses package B. Is B a dependency of your project?</summary>

Yes, a transitive (indirect) one. It gets installed and runs as part of your project, even though you never asked for it by name.
</details>

## Package managers

Finding, downloading and updating hundreds of packages by hand would be impossible. A **package manager** is a program that does it for you: you tell it what your project needs, and it fetches all of it, dependencies of dependencies included.

Packages are published to a **registry**: a huge online library of packages that the package manager downloads from.

| Language | Package manager | Registry | The project's list of packages |
| --- | --- | --- | --- |
| JavaScript | **npm** | the npm registry (npmjs.com) | `package.json` |
| Python | **pip** | PyPI, the Python Package Index | `requirements.txt` or `pyproject.toml` |

**npm** (Node Package Manager) comes with Node.js. The copy of Node that came with Groundwork includes npm too, and you'll use it in the next lesson. Remember from the *Code, languages* lesson that in PowerShell you type `npm.cmd` instead of `npm`, to avoid the script block.

## package.json, line by line

Every JavaScript project has a file called `package.json` in its main folder. You now know that it's JSON: an object of named values. Here's a typical one:

```json
{
  "name": "shop-website",
  "version": "1.0.0",
  "scripts": {
    "dev": "vite",
    "build": "vite build"
  },
  "dependencies": {
    "react": "^19.0.0",
    "react-dom": "^19.0.0"
  },
  "devDependencies": {
    "vite": "^7.0.0"
  }
}
```

| Name | What it holds |
| --- | --- |
| `name` | The project's name |
| `version` | The project's own version number |
| `scripts` | Short names for commands, like `dev` and `build`. That's the whole of the next lesson. |
| `dependencies` | Packages the project needs to **run** |
| `devDependencies` | Packages only needed while **working on** the project, such as tools that build or test it. Visitors to the website never need these. |

Inside `dependencies` and `devDependencies`, each line is a package name and the versions of it that are acceptable. `"react": "^19.0.0"` means "this project needs the package called react, version 19 or a newer 19-something".

(React and Vite are two hugely popular packages for building websites. You don't need to know what they do yet. They're just good examples.)

<summary>Quick check: in the package.json above, which package is only needed while working on the project?</summary>

Vite. It's listed under `devDependencies`.
</details>

## What happens when you install

When Groundwork's `start.bat` set itself up the first time, npm:

1. Read `package.json` to see what Groundwork needs.
2. Read `package-lock.json` (coming up shortly) to get the exact versions.
3. Downloaded every package, plus every package *those* need, from the npm registry.
4. Put them all in a folder called **`node_modules`**, inside the project's folder.

That's why the first start needed the internet, and later starts don't: everything is already in `node_modules`. Node knows to look in that folder when the code asks for a package.

The command to do this yourself is **`npm install`**. It reads package.json and fills node_modules.

## Version numbers

Most packages use **semantic versioning**: three numbers, `major.minor.patch`, like `19.2.1`.

| Part | Goes up when… | Safe to update? |
| --- | --- | --- |
| **Patch** (19.2.**1**) | Bugs are fixed | Almost always |
| **Minor** (19.**2**.0) | New features are added, nothing old is broken | Usually |
| **Major** (**19**.0.0) | Something works differently now | Maybe not: your code may need changes |

In `package.json`, versions are often written as a **range**, saying which versions are acceptable:

| Written as | Means |
| --- | --- |
| `"19.2.1"` | Exactly 19.2.1 |
| `"^19.2.1"` | 19.2.1 or any newer **19**.x. Not 20. |
| `"~19.2.1"` | 19.2.1 or any newer **19.2**.x |

The caret `^` is the most common. It's flexible, which is useful, but it means two installs a few months apart can get **different** versions, if new ones came out in between.

## Lockfiles

A **lockfile** fixes that. `package-lock.json`, which npm writes, records the **exact** version of every package that was installed, including all the hidden transitive ones.

- `package.json` says what you'd **accept**: "react, any 19.x".
- `package-lock.json` says exactly what you **got**: "react 19.2.1, and these 214 other packages at these exact versions".

**`npm ci`** installs exactly what the lockfile says, nothing newer. It's what servers and fresh setups should use, and it's what `start.bat` used for Groundwork. **`npm install`** may update the lockfile when versions have moved on.

| File or folder | Share it with the code? |
| --- | --- |
| `package.json` | Yes |
| `package-lock.json` | Yes, so everyone gets identical installs |
| `node_modules` | **No.** It's huge, and anyone can rebuild it from the two files above. |

Python's version of this: `pip install` installs packages, and `pip freeze > requirements.txt` writes the exact installed versions to a file.

<details>
<summary>Quick check: why can two people with the same package.json end up with different versions of a package?</summary>

Because ranges like `^3.1.0` allow newer versions. Without a lockfile, each install picks the newest version that fits the range at that moment.
</details>

## Trusting strangers' code

Every package runs with the same access as your own code. It can read your files and your environment variables, which often hold secrets, and it can send things over the internet. Most packages are written in good faith, but attackers do publish harmful ones, and occasionally break into real ones.

One trick is **typosquatting**: publishing a harmful package with a name one typo away from a popular one, and waiting for someone to mistype. You'll find a real example in the task.

AI tools add a new twist. As you saw in *When AI is confidently wrong*, they sometimes suggest package names that don't exist. Attackers notice which names AI tends to invent, and publish harmful packages under exactly those names.

Sensible habits:

- **Check the exact name**, letter by letter.
- **Look at its track record** on npmjs.com: weekly downloads, who publishes it, when it was last updated.
- **Prefer fewer, well-known packages.** Every package is something you're trusting.
- **Run `npm audit`** now and then. It checks your installed packages against a list of known security problems.

<ConsultantNote>
Auditing a client's dependencies is real, billable work: how many packages there are, how out of date, any known vulnerabilities, any abandoned ones. Old, unmaintained dependencies are behind a huge number of real security breaches.
</ConsultantNote>
