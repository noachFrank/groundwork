## In this lesson

- What **environment variables** are: settings that every program can read.
- What **PATH** is, and why "is not recognized as a command" happens.
- Why opening a new terminal fixes so many problems.
- How apps keep passwords and keys out of their code.

## Settings every program can see

An **environment variable** is a named piece of text that programs can read. It's a bit like a sticky note the computer hands to every program it starts: "the user's name is sam", "temporary files go here", and so on.

Windows sets lots of them. In PowerShell you read one by writing `$env:` followed by its name:

```powershell
$env:USERNAME      # prints: sam
$env:USERPROFILE   # prints: C:\Users\sam
$env:TEMP          # prints: C:\Users\sam\AppData\Local\Temp
```

(The `#` and the text after it are comments, for you to read. Typing just `$env:USERNAME` and pressing Enter shows the value.)

You saw `$env:TEMP` in a script back in *When AI is confidently wrong*. Now you know what it was: an environment variable holding the location of the temporary-files folder. And you know why the misspelled `$env:TMP_DIR` was dangerous: an environment variable that doesn't exist comes out as **empty text**.

You can set one yourself, too:

```powershell
$env:GREETING = "Hello"
```

### Each process gets its own copy

Here's the detail that explains a lot of confusing behavior. When a process starts another process, the new one gets a **copy** of the starter's environment variables. Programs **inherit** them from whatever started them.

- A program you start from a PowerShell window gets that window's variables.
- Change a variable in one PowerShell window, and only that window, plus programs started from it afterwards, see the change.
- Close the window, and the change is gone.

<details>
<summary>Quick check: you set `$env:GREETING` in one PowerShell window. Can a program started from a different window read it?</summary>

No. Each window is its own process with its own copy of the environment. Only that window, and programs started from it, have the change.
</details>

## PATH: how commands are found

The most important environment variable is **PATH**. It's a list of folders, separated by semicolons:

```text
C:\Windows\system32;C:\Windows;C:\Program Files\Git\cmd;C:\Users\sam\AppData\Local\Programs\Python\Python313;...
```

When you type a command name that isn't built into PowerShell, like `curl` or `node`, Windows does this:

1. Look in the first folder in PATH for a program with that name (like `node.exe`).
2. Not there? Try the next folder.
3. Keep going down the list.
4. Run the **first** match it finds.

If none of the folders has it, you get this:

```text
node : The term 'node' is not recognized as the name of a cmdlet, function, script file, or operable program.
```

That message almost never means the program is broken. It means **Windows couldn't find it** in any PATH folder.

That's why, in the last few lessons, you had to type Node's full path. Groundwork's Node lives in a folder that isn't on your PATH. In the task, you'll add that folder to the front of PATH, for one window, and then plain `node` will work.

`where.exe node` asks Windows "which folder would you find this in?", and lists every match in PATH order. It's the quickest way to check what's going on.

<details>
<summary>Quick check: two different versions of Node are installed in two PATH folders. Which one runs when you type `node`?</summary>

The one in whichever folder comes first in PATH. Windows stops at the first match.
</details>

### Why a new terminal fixes things

Installers usually add their program's folder to PATH for you. But remember: a terminal copies the environment **once, when it opens**. A window that was already open still has the old PATH, so it can't see the new program.

So after installing anything: **close the terminal and open a new one.** This fixes "not recognized" more often than anything else.

### Changing PATH for good

Changing `$env:PATH` in PowerShell only lasts as long as that window. You'll see this at the end of the task. To change it permanently, search the Start menu for **"Edit environment variables for your account"**. Usually, though, you let installers do it.

## Keeping secrets out of code

Programs often need secrets: passwords, database addresses, and API keys (from *Asking good questions*). Writing them straight into the code is a classic and serious mistake. Code gets shared, copied and kept forever, so anyone who gets the code gets the keys.

Instead, apps read them from environment variables. In JavaScript, `process.env.NAME` reads one:

```javascript
const apiKey = process.env.PAYMENT_API_KEY;
```

That line says: "make a name `apiKey` that holds whatever the PAYMENT_API_KEY environment variable says". The code itself contains no secret. Each computer that runs it provides its own.

During development, these settings often live in a file called `.env`, in the project's folder. Tools read it and turn each line into an environment variable:

```text
PAYMENT_API_KEY=sk_test_abc123
DATABASE_URL=postgres://localhost/shop
```

<Callout kind="warn" title="The .env rule">
A `.env` file must **never** be shared or uploaded with the code. You'll see how to stop that happening by accident in the Git module. Leaked keys get found and abused by automated programs within minutes.
</Callout>

<ConsultantNote>
When you review a client's code, search it for passwords and keys. Finding them written into the code, or a `.env` file shared with it, is one of the most common and serious problems in small companies' software, and one of the easiest to fix.
</ConsultantNote>
