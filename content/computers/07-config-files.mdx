## Settings live in text files

In the Bash lesson you met **config files**: files that hold a program's settings, like which port to listen on or what the shop is called.

Most config files are **plain text**. You can open them in Notepad and read them. But a program can't read loose sentences like "the port should be 3000, please". It needs the settings written in a **format**: a strict set of rules for how the text is laid out, so a program can read it reliably.

There are several common formats. Each has its own rules, and the most common mistake is breaking a rule by one character.

## JSON

**JSON** (said "jay-son", short for JavaScript Object Notation) is the most widely used format of all. It started in JavaScript, but now almost every language reads and writes it.

Here's a JSON file describing a shop:

```json
{
  "name": "Corner Shop",
  "open": true,
  "port": 3000,
  "products": ["bread", "milk", "eggs"],
  "owner": {
    "name": "Dina",
    "email": "dina@example.com"
  }
}
```

Let's take it apart.

### Objects: named values in curly braces

The whole thing is wrapped in curly braces `{ }`. In JSON, curly braces hold an **object**: a collection of **named values**. Each one is written as:

```text
"name": value
```

- The **name** (also called a **key**) is always in double quotes.
- Then a colon `:`.
- Then the **value**.
- Then a comma, if another named value follows.

So `"port": 3000` means "the setting called port has the value 3000".

### The kinds of values

| Kind | Looks like | Notes |
| --- | --- | --- |
| Text (a **string**) | `"Corner Shop"` | Always in **double** quotes |
| Number | `3000`, `4.99`, `-2` | No quotes |
| True or false | `true`, `false` | No quotes, all lower case |
| Nothing | `null` | Means "no value" |
| List (an **array**) | `["bread", "milk"]` | Square brackets, items separated by commas |
| Object | `{ "name": "Dina" }` | Curly braces, named values |

### Lists: values in order, in square brackets

`"products": ["bread", "milk", "eggs"]` is a **list**, called an **array** in JSON. Square brackets `[ ]` hold values in order, separated by commas.

Items in a list are numbered **starting from 0**, not 1. So `"bread"` is item 0, `"milk"` is item 1, and `"eggs"` is item 2. Nearly every programming language counts this way. It feels odd for a week, then normal forever.

### Nesting: things inside things

The value of `"owner"` is itself an object, with its own names and values. That's called **nesting**. Objects can hold lists, lists can hold objects, and it can go as deep as needed. Real JSON files are often nested several levels deep.

To describe where a value is, people often use dots: `owner.email` means "the email inside owner".

<details>
<summary>Quick check: in the shop JSON above, what's the value of `owner.name`? And what's item 2 of `products`?</summary>

`owner.name` is `"Dina"`. Item 2 of products is `"eggs"` (counting bread as 0 and milk as 1).
</details>

### Spaces and line breaks don't matter

These two mean exactly the same thing:

```json
{"name": "Corner Shop", "port": 3000}
```

```json
{
  "name": "Corner Shop",
  "port": 3000
}
```

Programs ignore the spacing. People spread JSON out over many lines, with indentation, purely so humans can read it. In the task you'll write it on one line, because that's easier to copy into a terminal.

## The rules that break most often

JSON is strict. One wrong character and a program refuses to read the whole file. These are the mistakes behind nearly every broken JSON file:

| Mistake | Wrong | Right |
| --- | --- | --- |
| Single quotes | `{'name': 'Dina'}` | `{"name": "Dina"}` |
| Name without quotes | `{name: "Dina"}` | `{"name": "Dina"}` |
| **Trailing comma** after the last item | `["bread", "milk",]` | `["bread", "milk"]` |
| Missing comma between items | `{"a": 1 "b": 2}` | `{"a": 1, "b": 2}` |
| A comment | `"port": 3000 // main port` | JSON has no comments at all |
| Capital True | `"open": True` | `"open": true` |

When a program can't read a JSON file, the error usually says something like `Unexpected token` or `Invalid JSON`, and often gives a **position**: how many characters into the file it got before it gave up. The real mistake is usually just before that point.

<details>
<summary>Quick check: what's wrong with `{"port": 3000, "debug": false,}`?</summary>

There's a comma after the last item, `false`, just before the closing brace. That's a trailing comma, and JSON doesn't allow it.
</details>

## YAML

**YAML** is another settings format. Files end in `.yml` or `.yaml`. It's designed to be easy for people to read, so it drops most of the punctuation:

```yaml
name: Corner Shop
open: true
port: 3000
products:
  - bread
  - milk
  - eggs
owner:
  name: Dina
  email: dina@example.com
```

That's exactly the same information as the JSON example.

- Each setting is `name: value` on its own line.
- **Indentation**, the spaces at the start of a line, shows what's inside what. `name: Dina` is indented under `owner:`, so it belongs to the owner.
- A dash `-` starts a list item.
- Comments are allowed, starting with `#`.

The catch: because indentation carries meaning, the number of spaces matters. One extra space can move a setting into the wrong place. And YAML must use spaces, never the Tab key.

YAML is popular for files that set up servers and automated jobs, including the one that publishes Groundwork's lessons. Groundwork's course outline, `curriculum.yaml`, is YAML too.

## .env files, again

You met `.env` files in the last lesson. They're the simplest of the three:

```text
PORT=3000
SHOP_NAME=Corner Shop
PAYMENT_API_KEY=sk_test_abc123
```

One `NAME=value` per line. No nesting, no lists. They're only used for environment variables, and they usually hold secrets, so they're never shared.

## Telling them apart

| You see | It's |
| --- | --- |
| Curly braces, double quotes everywhere, commas | JSON (`.json`) |
| `name: value` lines, indentation, dashes for lists | YAML (`.yml`, `.yaml`) |
| `NAME=value` lines, names in capitals | .env |

## Reading JSON from PowerShell

In the task, you'll have PowerShell read a JSON file. Three new pieces:

**`ConvertFrom-Json`** takes JSON text and turns it into something PowerShell understands, so you can ask for single values instead of seeing a wall of text.

**PowerShell variables.** In the Bash lesson you saw that a **variable** is a name that stores a value. PowerShell variables start with `$`, and you set one with `=`:

```powershell
$shop = Get-Content shop.json -Raw | ConvertFrom-Json
```

That reads the file, converts it from JSON, and stores the result under the name `$shop`. (`$env:PATH` from the last lesson is a special kind of variable. `$shop` is an ordinary one that you made.)

**Dots and square brackets** reach inside, just like the dotted descriptions above:

```powershell
$shop.name            # Corner Shop
$shop.owner.email     # dina@example.com
$shop.products[0]     # bread
```

Python and JavaScript, which you'll learn later, read JSON in almost exactly the same way. Once you can find your way around a JSON file, you can find your way around most data.

<ConsultantNote>
A large share of "the app suddenly won't start" calls come down to a settings file someone edited by hand. Knowing the JSON and YAML rules lets you find a missing comma in seconds, instead of reinstalling things that were never broken.
</ConsultantNote>
