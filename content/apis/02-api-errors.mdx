## In this lesson

When an API call fails, your code has to decide what to do about it. The status code is the API telling you which kind of failure it was. This lesson is about reading those codes and responding sensibly:

- **Client errors and server errors**, and why the difference decides whether to retry.
- The codes you'll meet most, beyond 404: **401 and 403**, **409 and 422**, and the **5xx** family.
- **Error bodies**: the details that come with an error.
- **Timeouts**, and requests that never get an answer at all.
- Python's **requests exceptions** and **`raise_for_status()`**.

## Whose problem is it?

You met the status families in *HTTP*. Here's what they mean for **your code**:

| Family | Whose problem | What to do |
| --- | --- | --- |
| **2xx** | Nobody's. It worked | Use the answer |
| **4xx** | **Yours**: something about the request | Fix the request. Sending the same thing again will fail the same way |
| **5xx** | **The server's**, at least for now | Wait a bit and try again, carefully |

That's the main idea. **Client errors** (4xx) need a change from you. **Server errors** (5xx) might go away on their own. One exception: **429 Too Many Requests** is a 4xx, but it means "slow down", so waiting and retrying is right. It gets its own lesson, *Pagination and rate limits*.

## The 4xx codes you'll meet

| Code | Means | Your code should… |
| --- | --- | --- |
| **400 Bad Request** | The request is malformed: broken JSON, a missing field | Fix the request |
| **401 Unauthorized** | "I don't know who you are." No credentials, or bad ones | Log in again, or fix the key. Alert someone if it's a script |
| **403 Forbidden** | "I know who you are, and you're not allowed" | Don't retry. You need more permission |
| **404 Not Found** | Nothing at that address | Check the id or address, or treat it as "doesn't exist" |
| **405 Method Not Allowed** | The address exists, but not for that method | Check the docs: maybe it's PATCH, not PUT |
| **409 Conflict** | Clashes with the current state, like a duplicate or an edit to an old version | Fetch the latest and decide |
| **415 Unsupported Media Type** | The body's format isn't accepted, often a missing `Content-Type: application/json` | Fix the header |
| **422 Unprocessable Content** | Understood, but the data isn't valid, like an unknown status | Fix the data |

The 401 versus 403 difference trips people up. 401 is about **who you are** (authentication), and 403 is about **what you may do** (authorization). You'll go deeper into both in the next lesson.

<details>
<summary>Quick check: you're logged in, but get 403 when trying to delete another user's order. Will logging in again help?</summary>

No. 403 means the server knows who you are and has decided you're not allowed. You'd need different permissions.
</details>

## The 5xx codes, and the server in the middle

| Code | Means |
| --- | --- |
| **500 Internal Server Error** | Something crashed inside the app. Often a bug |
| **502 Bad Gateway** | A server in the middle (a reverse proxy or load balancer) got a broken answer from the app behind it, or couldn't connect. Often the app has crashed or is restarting |
| **503 Service Unavailable** | Overloaded, or down for maintenance. Often comes with a **Retry-After** header saying how many seconds to wait |
| **504 Gateway Timeout** | The server in the middle gave up waiting for the app behind it |

502 and 504 come from the proxies and load balancers in the previous module. When you see them, the app behind is in trouble, not the proxy.

## Read the error body

A good API sends a JSON **error body** with details, for example:

```json
{"error": {"code": 422, "message": "\"lost\" isn't a status this API knows. Use one of: processing, shipped, delivered, cancelled"}}
```

The shape differs between APIs, so check their documentation. But always **log the body** along with the status. "422" on its own sends someone digging, while the message often says exactly what to fix.

<Callout kind="warn" title="200 with an error inside">
Some badly designed APIs answer `200 OK` with `{"error": "card declined"}`. Code that only checks the status thinks it worked. If you're stuck with such an API, check the body too, and mention it in your review.
</Callout>

## When there's no answer at all

Sometimes there's no status code, because no answer ever arrives:

- **Couldn't connect**: the server isn't running (connection refused), the name doesn't resolve, or a firewall is in the way.
- **Too slow**: the server accepted the connection but is taking forever.

By default, `requests` will wait **forever** for a slow server, and a stuck API can freeze your whole program. Always set a **timeout**, in seconds:

```python
response = requests.get(url, timeout=5)
```

## Catching these in Python

`requests` raises **exceptions** for the no-answer cases, and you catch them with `try` and `except`, as in *Reading errors and tracebacks*:

```python
try:
    response = requests.get(url, timeout=5)
except requests.Timeout:
    ...  # no answer within 5 seconds
except requests.ConnectionError:
    ...  # couldn't connect at all
```

- **`requests.Timeout`**: the timeout ran out.
- **`requests.ConnectionError`**: couldn't connect.
- To catch either with one `except`, list them in brackets: `except (requests.ConnectionError, requests.Timeout):`

Note that an error **status** like 404 is **not** an exception. The request worked, and the server answered "no". If you'd like error statuses to become exceptions too, call **`response.raise_for_status()`**. It raises `requests.HTTPError` for any 4xx or 5xx, and does nothing otherwise. Use it when any error should stop the code. When different errors need different handling, as in the task, check `.status_code` yourself.

## Retrying sensibly

For retryable errors (429, 500, 502, 503, 504, and no answer), the usual approach is:

1. **Wait** before trying again. If there's a `Retry-After` header, wait that long.
2. **Wait longer** after each failure, so a struggling server gets breathing room.
3. **Give up** after a few tries, and report it.
4. Be careful retrying a **POST**. It isn't idempotent, so if the first attempt actually worked, a retry could create a duplicate.

You'll write the waiting part in *Pagination and rate limits*. Stage 4 covers the rest properly.

<ConsultantNote>
"How does it handle errors?" is one of the most revealing questions about any integration. Scripts that ignore status codes, wait forever with no timeout, or retry everything (including 401s, all night) are extremely common, and they fail silently: orders quietly stop syncing and nobody notices for a week. Good error handling, plus an alert when it gives up, is often the difference between a minor blip and a lost month of data.
</ConsultantNote>
