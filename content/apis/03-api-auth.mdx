## In this lesson

In *APIs and JSON* you sent an API key in an `X-API-Key` header. That's one way for a program to prove who it is. This lesson covers the others, and why they exist:

- **Authentication** and **authorization**: two different questions.
- The **Authorization** header and **bearer tokens**.
- **Access tokens** that expire, and **scopes** that limit them.
- Getting a token with **client credentials**.
- How keys and tokens **leak**, and what to do when one does.

## Two different questions

Every protected API asks two separate questions:

1. **Authentication**: **who are you?** Proving your identity, with a key, a token or a password.
2. **Authorization**: **what are you allowed to do?** Checking that identity's permissions.

They fail differently. A missing or invalid credential gets **401 Unauthorized** (despite the name, it's about authentication). A valid credential without permission gets **403 Forbidden**. You saw both in the last lesson, and you'll get both from the practice API in the task.

## API keys: simple, but blunt

An **API key** is a long secret string that identifies a program. You've used one. Keys are popular because they're simple, but they have weaknesses:

- They usually **never expire**. A key leaked three years ago still works today.
- They're often **all-powerful**: one key can do everything the account can.
- Replacing one means updating every program that uses it, by hand.

They're fine for many server-to-server uses, as long as they're stored in environment variables and **rotated** (replaced with a new one, and the old one turned off) now and then, and immediately after any leak.

## Tokens: short-lived and limited

An **access token** is also a secret string, but it's **issued** for a purpose and has limits built in:

- It **expires**, often after an hour (`expires_in: 3600`). A leaked token is only useful for a short while. When it runs out, the program simply asks for a new one.
- It has **scopes**: a list of what it may do, like `reports:read` or `orders:write`. A token that can only read reports can't delete anything, even if it's stolen.

Tokens are sent in the standard **Authorization** header, with the word **Bearer** in front:

```text
Authorization: Bearer at_6d40877ec0e7e87ddd59
```

"Bearer" means "whoever holds this may use it". There's no extra check that it's really you, so a token has to be guarded like a password.

<details>
<summary>Quick check: a token is valid but only has the orders:read scope. It asks for the sales report, which needs reports:read. What status comes back?</summary>

403 Forbidden. The API knows who's calling (authentication worked) but that token isn't allowed to read reports (authorization failed).
</details>

## Getting a token: client credentials

Where does a program get a token? From a **token endpoint**: an address that hands out tokens in exchange for proof. For a program acting on its own behalf (not for a particular person), that proof is a **client id** and a **client secret**, issued when the program was registered with the service. This is called the **client credentials** flow:

```python
response = requests.post(BASE + "/oauth/token", data={
    "grant_type": "client_credentials",
    "client_id": "reports-app",
    "client_secret": "practice-secret",
    "scope": "reports:read",
})
token = response.json()["access_token"]
```

- **`data=`** sends the dictionary as **form fields**, the way an HTML form would, rather than as JSON. Token endpoints traditionally expect this format. (`json=` sends JSON, and the API's documentation says which one it wants.)
- `grant_type` says which kind of exchange this is.
- The answer includes the `access_token`, its `token_type` ("Bearer"), `expires_in` (seconds), and the `scope` it was given.

This is one part of a standard called **OAuth 2.0**. The next lesson covers its most famous part, "Log in with Google".

## Other things you'll see

- **Basic auth** sends a username and password with **every** request, in the Authorization header. They're only lightly encoded, not encrypted, so it's only acceptable over HTTPS, and tokens are usually better.
- **JWTs** (JSON Web Tokens, said "jots") are a very common token format. A JWT is three chunks of text separated by dots. The middle chunk holds readable details, like who it's for, its scopes and when it expires, and the last is a signature proving the server issued it. Anyone can **read** a JWT, so it must never hold secrets. They return in Stage 4.
- **Sessions and cookies** from *Cookies and sessions* do the same job for websites in a browser. Tokens are more common for mobile apps and programs calling APIs.

## How credentials leak

The usual ways, all of them common:

- **Committed to Git**, even "just for a minute". It's in the history forever, as you saw in Stage 1, and bots scan public repositories for keys within minutes.
- **Put in browser code**, where anyone can read it with F12.
- **Written to logs**: printing a URL or headers that contain a key. The flaw task is exactly this.
- **Pasted into chats, tickets or AI assistants** while asking for help.

When one leaks, the order matters: **revoke or rotate it first**, then clean up. Deleting it from the code doesn't help while the old key still works.

<Callout kind="warn" title="Least privilege">
Give each program its own credential, with only the scopes it needs. If the reporting tool's token leaks, the attacker can read reports and nothing else, and you can cancel just that one. This idea is called **least privilege**, and Stage 4 builds on it.
</Callout>

<ConsultantNote>
Ask early in any engagement: "Where are your API keys, who can see them, and when were they last rotated?" You'll often find one all-powerful key shared by five systems and two ex-employees, written in a document. Moving to one scoped credential per system, kept in environment variables or a secret manager, is a cheap, high-value recommendation, and it makes the next leak a ten-minute fix instead of a crisis.
</ConsultantNote>
