## In this lesson

Two limits every real API has, and every integration has to handle:

- **Pagination**: long lists come a page at a time. You'll learn page numbers, cursors and **next links**, and how to collect everything.
- Python's **`while` loop**, which repeats until a condition becomes false.
- **Rate limits**: how many requests you may send in a given time, the **429** status, the headers that report where you stand, and **Retry-After**.
- **Backoff**: waiting longer after each failure.
- **Quotas**: limits per day or month, often tied to what you pay.

## Pagination: a page at a time

A shop might have 2,000 products. Sending them all in one answer would be slow to build, slow to send and slow to read, and most callers only want the first few. So APIs **paginate**: they send one page and tell you how to get the next.

Groundwork's practice API does it like this:

```text
GET /products?page=1&per_page=5
```

```json
{
  "items": [{"id": 1, "name": "Desk lamp", "price": 2}, "…four more…"],
  "page": 1,
  "per_page": 5,
  "total": 23,
  "total_pages": 5,
  "next": "/products?page=2&per_page=5"
}
```

- `items` holds this page's products.
- `total` and `total_pages` say how many there are altogether.
- **`next`** is the address of the next page, or `null` (Python's `None`) on the last one.

A ready-made **next link** like that is the friendliest design: you just follow it, without working out page numbers yourself.

### Page numbers or cursors

There are two common styles:

- **Page numbers** (`?page=3&per_page=50`) are simple, and you can jump to any page. But if items are added or removed while you're reading, things shift between pages, and you can miss or repeat one.
- **Cursors** (`?after=prod_8f2a&limit=50`) mean "continue after this item". The answer gives you the cursor for the next call. They stay correct while the list changes, which is why big APIs like Stripe and Slack use them.

Either way, the loop is the same: fetch, keep the items, move on, until there's nothing more.

## The while loop

A `for` loop goes through something you already have, like a list. Here you don't know how many pages there are until you've read them. For that, Python has **`while`**: it repeats its block **as long as a condition is true**, checking before each round:

```python
url = BASE + "/products?per_page=5"
while url is not None:
    page = requests.get(url).json()
    # … keep this page's items …
    if page["next"] is None:
        url = None
    else:
        url = BASE + page["next"]
```

Read it as "while there's a page to fetch: fetch it, keep its items, then work out the next address". On the last page, `url` becomes `None`, the condition is false, and the loop ends.

<Callout kind="warn" title="Make sure it can end">
A `while` loop only stops when its condition becomes false. If nothing inside the loop ever changes that, it runs forever. This is an **infinite loop**. In the terminal, **Ctrl+C** stops it. In Groundwork's editor, Python that runs too long is stopped for you. Before running a `while` loop, ask: "what makes this condition false?"
</Callout>

<details>
<summary>Quick check: in the loop above, what makes it stop?</summary>

On the last page, `next` is `None`, so `url` is set to `None`, and `while url is not None` becomes false.
</details>

## Rate limits

A **rate limit** caps how many requests one caller may send in a window of time, like "100 requests per minute per API key". It protects the service from overload and from one runaway script, and it shares capacity fairly. Exceed it, and you get:

```text
HTTP/1.1 429 Too Many Requests
Retry-After: 42
```

**429 Too Many Requests** is the "slow down" status. **Retry-After** says how many seconds to wait.

Most APIs also tell you where you stand on **every** response, before you hit the limit:

| Header | Means |
| --- | --- |
| `X-RateLimit-Limit: 100` | Requests allowed per window |
| `X-RateLimit-Remaining: 12` | Requests left in this window |
| `X-RateLimit-Reset: 30` | Seconds until the window resets (some APIs give a clock time instead) |

The exact names vary, so check the API's documentation. The practice API's `/limited` address allows 5 requests per minute per `X-Client-Id`. In the task you'll call it until it says 429, then read Retry-After from `response.headers`.

## Waiting politely: backoff

When you get a 429, or a temporary 5xx error, the worst thing to do is retry immediately. Lots of clients doing that at once keep the server overloaded. Instead:

1. If there's a **Retry-After**, wait exactly that long.
2. If not, **back off**: wait longer after each failed attempt. A common pattern doubles the wait: 1 second, then 2, 4, 8… up to a maximum, like a minute. In Python, `2 ** attempt` means 2 to the power of `attempt`: `2 ** 0` is 1, `2 ** 3` is 8.
3. Give up after a few attempts, and report it.

That's **backoff**. Stage 4 adds a twist: a little randomness, so a thousand clients don't all retry at the same instant.

## Staying under the limit in the first place

Waiting handles a 429, but good design avoids most of them:

- **Batch**: many APIs accept many items per request. 100 products per call instead of 1 is 100 times fewer requests.
- **Send only what changed**, rather than everything every time.
- **Cache** answers that don't change often.
- **Spread work out** instead of sending bursts.

Separate from per-minute rate limits, many APIs also have a **quota**: a total per day or month, often tied to the plan you pay for. Going over can mean errors until the month resets, or a surprise bill. Paid AI APIs work this way, which matters in Stage 3.

<ConsultantNote>
Rate limits and quotas belong in every integration estimate. "How many requests will this need per day, and what does the API allow on the client's plan?" is a five-minute calculation that can change a design completely. It's far better to find out in a planning meeting than in production on launch day.
</ConsultantNote>
