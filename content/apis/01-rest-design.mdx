## In this lesson

In *APIs and JSON* you met REST and called an API to read orders. This module goes deeper into APIs, starting with how a good one is **designed**. That matters even if you never build one, because you'll judge them, and a well-designed API is easier and safer to use:

- **Resources** and **collections**: nouns in the address.
- The four everyday actions (**CRUD**) and their methods, including **PUT versus PATCH**.
- **Query strings** for filtering, and **nested** addresses.
- **Safe** and **idempotent** methods: which requests can be repeated without harm.
- **201**, **204** and the **Location** header.

## Nouns in the address, verbs in the method

REST's central idea fits in one sentence: **the address names a thing, and the method says what to do with it.**

- A **resource** is one thing the API knows about: order 102, customer 7, invoice 5501. Its address is like `/orders/102`.
- A **collection** is the set of all things of one kind: `/orders`. It's usually plural.

The methods do the rest. Almost everything an app does to data is one of four actions, called **CRUD** (create, read, update, delete):

| Action | Request | Typical answer |
| --- | --- | --- |
| **Create** an order | `POST /orders` with the details as JSON | `201 Created`, with the new order |
| **Read** all orders | `GET /orders` | `200 OK`, with a list |
| **Read** one order | `GET /orders/102` | `200 OK`, or `404 Not Found` |
| **Update** part of an order | `PATCH /orders/102` with the changed fields | `200 OK`, with the updated order |
| **Replace** a whole order | `PUT /orders/102` with every field | `200 OK` |
| **Delete** an order | `DELETE /orders/102` | `204 No Content` |

So there's no `/getOrders`, `/createOrder` or `/deleteOrder`. Once you know an API is RESTful and has orders, you can almost guess its addresses.

## PUT versus PATCH

Both change an existing resource, but differently:

- **PUT** means "**replace** it with exactly this". You send the **whole** resource. Anything you leave out could be wiped.
- **PATCH** means "**change** just these fields". `PATCH /orders/104` with `{"status": "shipped"}` changes the status and leaves everything else alone.

Many APIs use PATCH for everyday edits because it's harder to get wrong. Groundwork's practice API refuses a PUT that's missing fields, with a 400 explaining why. The task's `ship()` needs PATCH.

## 201, 204 and Location

Two success codes you'll see constantly in REST APIs:

- **201 Created** answers a POST that made something. A good API also sends a **Location** header with the new resource's address, like `Location: /orders/104`, and usually the new resource in the body, including its new `id`.
- **204 No Content** means "done, and there's nothing to send back". It's typical after a DELETE. There's no body, so don't call `.json()` on it.

## Filtering with query strings

A list can be huge, so APIs let you ask for just part of it with a **query string**: everything after a `?` in the address, as `name=value` pairs joined by `&`:

```text
GET /orders?customer=Ada&status=shipped
```

It's the standard way to **filter**, **search** and **sort**. Asking the API to filter is much better than downloading everything and filtering in your own code, because the server does the work and sends far less.

In Python, `requests` builds the query string for you with **`params=`**:

```python
requests.get(BASE + "/orders", params={"customer": "Ada", "status": "shipped"})
```

It turns the dictionary into `?customer=Ada&status=shipped`, and safely encodes any spaces or symbols, which is easy to get wrong when gluing text together yourself.

### Nested addresses

When one thing belongs to another, a **nested** address can read naturally: `/customers/7/orders` means "customer 7's orders". It's the same as `/orders?customer_id=7`, and both styles are common. Keep nesting to one level, because `/customers/7/orders/102/items/3/notes` gets unwieldy fast.

## Safe and idempotent: can I send it again?

Networks fail. A request times out, and you don't know whether it arrived. Can you just send it again? That depends on the method, and REST gives two promises:

- **Safe** methods only **read**. GET is safe. It must never change anything, which is why browsers, caches, link previews and search engines send GET requests freely.
- **Idempotent** methods have the **same effect whether you send them once or five times**. GET, PUT and DELETE are idempotent: deleting order 102 twice still leaves it deleted (the second attempt probably answers 404, but nothing extra happens). **POST is not**: sending "create an order" twice usually creates **two** orders.

| Method | Safe? | Idempotent? |
| --- | --- | --- |
| GET | Yes | Yes |
| PUT | No | Yes |
| DELETE | No | Yes |
| PATCH | No | Usually not guaranteed |
| POST | No | No |

That's why the API review task's `GET /orders/102/delete` is dangerous, and why retrying a POST needs care. Stage 4 covers how payment APIs make POST safe to retry.

## Sending changes from Python

The `requests` methods match the HTTP methods:

```python
KEY = {"X-API-Key": "practice-key"}

requests.post(BASE + "/orders", json={"customer": "Lin", "item": "Desk lamp", "total": 35}, headers=KEY)
requests.patch(BASE + "/orders/104", json={"status": "shipped"}, headers=KEY)
requests.delete(BASE + "/orders/104", headers=KEY)
```

- **`json=`** turns a Python dictionary into a JSON body and sets the `Content-Type: application/json` header for you.
- **`headers=`** adds headers, here the API key. The practice API answers 401 without it.

<ConsultantNote>
When you evaluate a vendor's API for a client, design quality is a real signal. Consistent nouns, correct methods, proper status codes and filtering on the server usually mean a careful team and fewer surprises. Verbs in addresses, GETs that change data, and "200 OK" with an error message inside usually mean a long, expensive integration. Say so early, before the client commits.
</ConsultantNote>
