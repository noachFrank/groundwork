## In this lesson

"Log in with Google", "Connect your Dropbox", "Allow this app to post to your calendar". They all use one standard: **OAuth**. This lesson walks through it slowly, because it looks complicated until you see that every step has a reason:

- The problem OAuth solves: **delegated access**.
- The four **roles**, and the **authorization code flow**, step by step.
- The **state** check, and why the **client secret** must stay on a server.
- **Refresh tokens**, **OpenID Connect** and **PKCE**, briefly.
- **`encodeURIComponent()`**, for building the links.

## The problem

Before OAuth, if a printing app wanted your photos from another service, it asked for your **password** for that service. That was terrible:

- The app could do **anything** with your account, not just read photos.
- You couldn't cancel its access without changing your password, which also locked out everything else.
- If the app was hacked, so was every user's account.

OAuth's answer is **delegated access**: you let the app do **one specific thing** on your behalf, with a token you can cancel, and your password never leaves the service you log in to.

## Four roles

| Role | In our example |
| --- | --- |
| **The user** (resource owner) | You |
| **The client**: the app that wants access | PhotoPrint |
| **The authorization server**: where you log in and approve | Google's sign-in |
| **The resource server**: the API with your stuff | Google Photos API |

Before any of this, PhotoPrint registered with Google and got a **client id** (public) and a **client secret** (private), and told Google its **redirect URI**: the exact address where users should be sent back.

## The authorization code flow

Step through it:

<Viz name="oauth-flow" />

In words:

1. **Send the user to the authorization server.** PhotoPrint sends your browser to a link like:

   ```text
   https://accounts.example/authorize?response_type=code&client_id=photoprint
     &redirect_uri=https%3A%2F%2Fphotoprint.example%2Fcallback
     &scope=photos.read&state=x7Kq2
   ```

   It says who's asking (`client_id`), what it wants (`scope`), where to send you back (`redirect_uri`), and a random `state` (more on that below).

2. **You log in and approve.** On Google's own page, so PhotoPrint never sees your password. Google shows a **consent screen**: "PhotoPrint wants to: see your photos. Allow?"

3. **Back to the app, with a code.** Google sends your browser to the redirect URI with a short-lived, single-use **authorization code**: `https://photoprint.example/callback?code=Splx10BeZQ&state=x7Kq2`.

4. **Swap the code for tokens, server to server.** PhotoPrint's **server** sends the code, plus its **client secret**, directly to Google's token endpoint. Google answers with an **access token** (and often a **refresh token**).

5. **Use the token.** PhotoPrint calls the Photos API with `Authorization: Bearer …`, exactly as in the last lesson.

Why the extra step with a code, instead of putting the token straight in the redirect? Because the redirect travels through the browser, where addresses end up in history and logs. The code is useless without the client secret, and it works only once, for a few minutes.

<details>
<summary>Quick check: at which step does the client secret get used, and where?</summary>

Step 4, when the app's server swaps the code for tokens. It's sent server to server, never through the browser.
</details>

## The state check

When the user comes back to the redirect URI, how does the app know this reply belongs to a login **it** started? An attacker could start a login with **their own** account, then trick you into opening the callback link with **their** code. Your session would then be connected to the attacker's account, and anything you upload goes to them.

So before step 1, the app makes a random **state** value and remembers it (in the user's session). When the user comes back, it checks that the `state` in the reply **matches exactly**. No match, no login. You'll write that check in the JavaScript task.

## The client secret stays on the server

The swap in step 4 needs the **client secret**, and the same rule applies as for API keys: anything in browser code is public. If the secret is in frontend JavaScript, anyone can read it and pretend to be the app.

So the flow above is for apps **with a server**. Apps with no server of their own, like single-page web apps and mobile apps, use an addition called **PKCE** (said "pixie"). The app makes a random one-time secret at the start of each login, sends a scrambled version in step 1, and the real one in step 4. A stolen code is useless without it, and nothing permanent has to be hidden in the app.

<Callout kind="warn" title="A very common AI mistake">
Ask an AI for "Google login in React" and it may put the client secret, or the whole code exchange, in the frontend. That's the API-key-in-the-browser mistake again. The exchange belongs on your server, or the app should use PKCE.
</Callout>

## Refresh tokens

Access tokens expire, often after an hour. Asking the user to log in and approve again every hour would be awful. So the token endpoint can also hand out a **refresh token**: a long-lived credential, kept safely on the server, used for one thing only: getting a **new access token** when the old one expires.

The typical pattern, which you'll code in the Python task:

1. Call the API with the access token.
2. If it answers **401** because the token expired, POST the refresh token to the token endpoint (`grant_type=refresh_token`).
3. Retry the call with the new access token, **once**.

Users can cancel an app's access in their account settings ("Third-party apps with account access"). That revokes the refresh token, and the app has to ask again.

## OpenID Connect: logging in, not just access

OAuth itself is about **access**: what an app may do. "Log in with Google" needs **identity**: who you are. **OpenID Connect** is a thin layer on top of OAuth that adds exactly that: along with the access token, the app gets an **ID token** saying who logged in. When people say "we use OAuth for login", they usually mean OpenID Connect.

## JavaScript: encodeURIComponent

A query string can't contain raw spaces, `&`, `/` or `?` inside a value, because they'd be confused with the address's own structure. **`encodeURIComponent()`** replaces such characters with `%` codes:

```javascript
encodeURIComponent("https://photoprint.example/callback")  // "https%3A%2F%2Fphotoprint.example%2Fcallback"
encodeURIComponent("photos.read profile")                  // "photos.read%20profile"
```

`%3A` is a colon, `%2F` is a slash, and `%20` is a space. Python's `params=` does the same thing for you automatically.

<ConsultantNote>
"Can we let users log in with Google or Microsoft?" and "can we connect to the client's Salesforce?" are everyday requests, and both are OAuth. Knowing the flow lets you estimate the work honestly (registering the app, the consent screen, storing refresh tokens safely, handling revoked access) and review it properly. Where is the client secret? Is state checked? Are tokens stored encrypted? Those questions catch real bugs.
</ConsultantNote>
