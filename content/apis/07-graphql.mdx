## In this lesson

Most APIs you'll meet are REST. The second most common style for public and app APIs is **GraphQL**, created at Facebook for exactly the problem in the Predict question. This lesson covers:

- The two problems it solves: **over-fetching** and **under-fetching**.
- Writing a **query**, with nesting and arguments.
- The **schema**, **variables** and **mutations**.
- Why errors arrive with **200 OK**.
- The **trade-offs**: when GraphQL is worth it, and when it isn't.

## The problem with lots of little requests

Picture a phone app's order screen showing each order's item and the customer's city. With the REST API from earlier lessons:

1. `GET /orders` returns every order, with every field, when the screen needs one.
2. Then `GET /customers/1`, `GET /customers/2`… once per customer, each returning the whole customer, to read one field.

Two problems:

- **Over-fetching**: getting far more data than you need.
- **Under-fetching**: one request doesn't get everything, so you need several, and each costs a round trip. On a phone network, that's the slow part.

REST teams often respond by building special endpoints for each screen, like `/order-screen-data`. That works, until there are fifty screens across three apps.

## One endpoint, one query

GraphQL has **one** address, usually `/graphql`, and you POST a **query** that describes the exact shape of data you want:

```graphql
{
  orders(customer: "Ada") {
    item
    customer {
      city
    }
  }
}
```

The answer has **exactly that shape**, wrapped in `data`:

```json
{
  "data": {
    "orders": [
      {"item": "Keyboard", "customer": {"city": "London"}},
      {"item": "USB cable", "customer": {"city": "London"}}
    ]
  }
}
```

Read the query from the outside in:

- `orders` is a **field** the API offers at the top level. `(customer: "Ada")` is an **argument**, like a filter.
- Inside the braces, you list the fields you want from each order: `item`.
- `customer` is a field whose value is another object, so it gets its own braces, listing the fields wanted from it: `city`. That nesting follows related data, in the **same** request.

One round trip, and nothing extra. That's the whole appeal.

<details>
<summary>Quick check: how would you change the query to also get each order's total?</summary>

Add `total` inside the order's braces, next to `item`. You only get the fields you list.
</details>

## The schema

How do you know which fields exist? Every GraphQL API has a **schema**: a typed list of everything it offers. The practice API's, roughly:

```graphql
type Query {
  orders(customer: String, status: String): [Order]
  order(id: Int!): Order
  customers: [Customer]
}

type Order {
  id: Int
  item: String
  total: Float
  status: String
  customer: Customer
}

type Customer {
  id: Int
  name: String
  city: String
  orders: [Order]
}
```

`[Order]` means a list of orders, `Int!` means a whole number that must be given, and `Float` is a number with decimals. The schema does the same job as an OpenAPI file, but it's built into GraphQL itself, so tools can read it from the API and offer autocomplete as you type a query.

## Variables

In the task, the customer's name changes on every call. You **could** paste it into the query text, but don't. That's the same mistake as gluing text into SQL, which you met as **injection** in the debugging lesson: a name with a quote in it breaks the query, and an attacker could add extra parts. Use **variables** instead:

```graphql
query ($customer: String) {
  orders(customer: $customer) { item }
}
```

and send the values separately, alongside the query:

```python
requests.post(BASE + "/graphql", json={
    "query": query,
    "variables": {"customer": "Ada"},
})
```

`$customer` is a placeholder, declared at the top with its type. The server fills it in safely.

<Callout title="Braces and f-strings don't mix">
GraphQL is full of `{` and `}`, and so are Python f-strings. Writing a query inside an f-string means doubling every brace (`{{`), which is easy to get wrong. One more reason to use plain triple-quoted strings and variables.
</Callout>

## Mutations

Reading is a **query**. Changing data is a **mutation**, written the same way, and naming the fields you want back from the result:

```graphql
mutation {
  createOrder(customer: "Sam", item: "Pen", total: 3) {
    id
    status
  }
}
```

## Errors come back with 200

This catches everyone out. Ask the practice API for a field that doesn't exist:

```json
{"data": null, "errors": [{"message": "Cannot query field \"price\" on type \"Order\". ..."}]}
```

The status code is **200 OK**. GraphQL usually reports problems **inside the body**, in an `errors` list, partly because one query can partly succeed. So GraphQL code must check for `errors`, not just the status code. The task's `has_errors` does exactly that.

## The trade-offs

GraphQL isn't simply better than REST. It moves work around:

| Benefit | Cost |
| --- | --- |
| One request per screen, with exactly the data needed | Every request is a POST to one address, so ordinary HTTP caching (and CDNs) help much less |
| Frontend teams don't wait for new endpoints | The client chooses the query, so one huge, deeply nested query can overload the server. You need limits on depth and cost |
| A typed schema, with great tools | A schema, a server library and resolvers to build and maintain |
| Many different apps share one API | Errors and monitoring work differently from REST, so teams have to learn new habits |

A useful rule: GraphQL shines when **many different clients** (web, iPhone, Android, partners) need **different combinations of related data**. For one website talking to its own simple backend, REST is usually simpler and cheaper.

<ConsultantNote>
Clients sometimes ask for GraphQL because it sounds modern. Ask who the API's clients are and how different their needs are. If the answer is "our one website", REST is almost always the cheaper choice. If it's "four apps and partners, and the mobile team is drowning in requests", GraphQL can genuinely pay for itself. Either way, insist on query limits before it goes live.
</ConsultantNote>
