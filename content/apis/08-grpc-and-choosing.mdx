## In this lesson

You've now met REST, GraphQL, polling, server-sent events and WebSockets. This lesson adds the last major style, **gRPC**, and then pulls everything together:

- **RPC**: calling a function on another computer.
- **gRPC**, **protobuf** and **.proto files**: a strict, shared contract.
- **Binary formats**, **generated code** and **streaming**.
- A practical guide to **choosing an API style**.

## Calling a function on another computer

REST thinks in **resources**: nouns in the address, and verbs as methods. Another long-standing approach thinks in **functions**: "call `GetPrice` with these inputs, and give me the result". When the function runs on another computer, that's a **remote procedure call**, or **RPC**. Your code looks like it's calling an ordinary function, and the library does the network part.

```python
price = pricing.GetPrice(product_id=42, country="GB")
```

## gRPC

**gRPC** is the most popular modern RPC system, created at Google. Three things set it apart.

### 1. A shared contract: the .proto file

Everything starts with a **.proto file** describing the service's functions and the exact shape of every message:

```protobuf
service Pricing {
  rpc GetPrice (PriceRequest) returns (PriceReply);
}

message PriceRequest {
  int32 product_id = 1;
  string country = 2;
}

message PriceReply {
  int64 price_in_pennies = 1;
  string currency = 2;
}
```

- `service Pricing` with `rpc GetPrice (...) returns (...)` declares a function and its input and output types.
- Each `message` lists its fields, with **types** (`int32` is a whole number, `string` is text) and a **field number** (`= 1`, `= 2`). The numbers, not the names, are what's actually sent, which keeps messages small, and lets fields be renamed later without breaking anything.

It's the same idea as an OpenAPI file or a GraphQL schema, but stricter.

### 2. Generated code

From that one file, a tool **generates** code for each language: a ready-made client for the caller and a skeleton for the server, in Python, Go, Java, C#, JavaScript and more. This is **code generation**. Both sides are built from the same contract, so they can't disagree about what a message contains. A mistake shows up when the code is built, not as a confusing failure in production.

### 3. Compact binary messages over HTTP/2

JSON is **text**: readable, but bulky. `{"product_id": 42, "country": "GB"}` repeats the field names in every message. gRPC uses **Protocol Buffers** (**protobuf**), a **binary format**: compact bytes that only make sense with the .proto file. Messages are often several times smaller and faster to process.

It runs over **HTTP/2**, so many calls share one connection at once (multiplexing, from *Faster HTTP*). HTTP/2 also allows **streaming**: either side, or both, can send a flow of messages over a single call, for example a server streaming price updates, or a client uploading a long series of readings.

<details>
<summary>Quick check: why are protobuf messages smaller than JSON?</summary>

They're binary, and they send short field numbers instead of repeating field names as text in every message.
</details>

## Where gRPC fits, and where it doesn't

**Good fit:** calls **between your own internal services**, especially at high volume, where speed and strict agreement matter, and all the teams can share the .proto files. Many large systems use gRPC inside and REST at the edge.

**Poor fit:**

- **Browsers.** They can't speak normal gRPC. It needs a translating proxy called **gRPC-Web**.
- **Public and partner APIs.** Outsiders need the .proto files and gRPC tools, and they can't just try it with curl.
- **Debugging by eye.** Binary messages can't be read in a log or the Network tab without extra tools.

## Choosing an API style

There's no single best style. Each fits a kind of job:

| Situation | Usually choose | Why |
| --- | --- | --- |
| A public or partner API, or "we're not sure yet" | **REST** | Everyone understands it, every language and tool supports it, and HTTP caching works |
| Many different apps need different mixes of related data | **GraphQL** | One request per screen, exactly the data needed |
| Fast, high-volume calls between your own services | **gRPC** | Compact, strictly typed, with generated code and streaming |
| Telling another company's server when something happens | **Webhooks** | Server-to-server notifications without polling (next module) |
| Live updates to a browser or app | **WebSockets** or **SSE** (or polling, if a delay is fine) | Push instead of asking |

Three principles behind the table:

1. **Start with REST** unless there's a specific reason not to. It's the default for good reasons.
2. **Choose per job, not per company.** It's normal to have REST for partners, gRPC inside, and WebSockets for a live dashboard.
3. **The team matters.** A style nobody on the team knows has a real cost in learning, bugs and hiring. Name that cost when you recommend it.

<ConsultantNote>
Technology debates inside client teams ("we should move everything to gRPC!") are common, and they're often about taste. Your value is turning them into criteria: who calls this API, how often, from where, and who maintains it? Answered honestly, those questions usually settle the argument, and a written decision ("REST for partners because…, gRPC for pricing because…") stops it coming back every six months.
</ConsultantNote>
