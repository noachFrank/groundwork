## In this lesson

An API is a promise: "send this, and I'll answer like that". This lesson is about what happens when that promise has to change, and how to read the promise in the first place:

- **Breaking** and **non-breaking** changes.
- **Versioning**, and the **Deprecation** and **Sunset** warnings.
- **Changelogs**.
- **OpenAPI**, the standard way to describe an API, and **Swagger UI**.
- **SDKs**, and a **checklist** for reading any API's docs.

## When a change breaks things

Hundreds of programs might be calling an API, written by people the API's team has never met. Any change to what those programs depend on can break them.

**Breaking changes** include:

- Removing or renaming a field, like `name` becoming `first_name` and `last_name`.
- Changing a field's type or meaning, like a price changing from pounds to pennies.
- Removing an endpoint, or changing its address or method.
- Requiring a new input that callers don't send.

**Non-breaking changes** are usually additions: a new optional field, a new endpoint, a new optional query parameter. Well-written code ignores fields it doesn't recognize, so adding things rarely hurts.

## Versions

When a breaking change is needed, a good API releases it as a **new version**, and keeps the old one working while callers move across. Three common styles:

| Style | Looks like | Used by |
| --- | --- | --- |
| In the address | `/v1/customers`, `/v2/customers` | Most APIs |
| In a header | `Accept-Version: 2` | Some |
| By date | `Stripe-Version: 2024-06-20` | Stripe and others |

The practice API has both `/v1/customers/1` and `/v2/customers/1`. Compare them:

```json
{"id": 1, "name": "Ada Lovelace", "city": "London"}
```

```json
{"data": {"id": 1, "first_name": "Ada", "last_name": "Lovelace",
          "email": "ada.lovelace@example.com", "address": {"city": "London"}}}
```

v2 splits the name, adds an email, moves the city inside `address`, and wraps everything in `data`. Any one of those changes would have broken a v1 caller.

<details>
<summary>Quick check: an API adds a new optional field, `phone`, to its customer answers. Breaking or not?</summary>

Not breaking. Existing callers just ignore the new field.
</details>

## Deprecation and sunset

An old version can't live forever. The polite way to retire it:

1. **Deprecate** it: announce that it's on its way out, while it keeps working. Many APIs add a header to every old-version response: `Deprecation: true`.
2. Set a **sunset** date, after which it stops working: `Sunset: Thu, 31 Dec 2026 23:59:59 GMT`.
3. Point to the replacement, often with a `Link` header: `Link: </v2/customers/1>; rel="successor-version"`.

Request `/v1/customers/1` with `curl.exe -i` and you'll see all three from the practice API. Checking for that `Deprecation` header in your own scripts is a cheap early warning, and you'll do exactly that in the task.

## Changelogs

A **changelog** is a dated list of what changed in each release, with breaking changes clearly marked. It's the first thing to read when an integration suddenly fails, and the thing to check regularly for any API a client depends on. Versions often follow the **semantic versioning** you met with packages: a bump in the first number (2.x to 3.0) means breaking changes.

## OpenAPI: a description computers can read

API documentation used to be hand-written web pages, often out of date. Most modern REST APIs are also described in an **OpenAPI** file (it used to be called **Swagger**): a YAML or JSON file listing every endpoint, its parameters, its possible responses and how to authenticate. A small piece:

```yaml
paths:
  /invoices:
    get:
      summary: List invoices
      parameters:
        - name: status
          in: query
          schema: { type: string, enum: [draft, sent, paid, overdue] }
      responses:
        "200": { description: A page of invoices }
        "401": { description: Missing or invalid API key }
```

Read it top-down, like any YAML from *Settings files*: under `paths`, the address `/invoices`, then the method `get`, then its `parameters` (`status`, in the query string, one of four values) and its `responses`, keyed by status code. `enum` means "one of these values".

Because it's machine-readable, tools can do a lot with it:

- **Swagger UI** turns it into interactive documentation, where you can read each endpoint and send test requests from the page.
- Postman can import it as a ready-made collection of requests.
- Code generators can produce an **SDK**: a library in your language that wraps each request in an ordinary function, like `client.invoices.list(status="overdue")`.

You'll read a real-looking extract in the second task.

## Reading any API's docs: a checklist

Whether it's an OpenAPI file or a set of web pages, look for these, in roughly this order:

1. **Base URL and version.** Where requests go, and which version you're on.
2. **Authentication.** Keys, tokens or OAuth? Which header? How are credentials obtained and rotated?
3. **The endpoints you need**, with their parameters, request bodies and responses.
4. **Errors.** The error body's format, and what each status means for this API.
5. **Rate limits and quotas.** Per minute, per day, and on which plan.
6. **Pagination.** Pages or cursors?
7. **A sandbox or test mode**, so you can try things without real money or real customers.
8. **The changelog and deprecation policy.** How much warning do they give before breaking changes?

If a vendor can't answer most of these, that's important information for your client.

"How long will the integration take?" depends heavily on the docs. Ten minutes with this checklist before you estimate tells you whether it's a two-day job or a two-week job. Missing rate-limit details, no sandbox or no deprecation policy are all risks to write into your estimate, and to raise with the client before they sign with that vendor.
