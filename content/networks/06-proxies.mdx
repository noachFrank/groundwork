## In this lesson

So far, requests have gone straight from a browser to a server. In real life there's usually something **in the middle**. This lesson covers:

- What a **proxy** is, and the two kinds: **forward** and **reverse**.
- Why almost every real website sits behind a **reverse proxy**, and the jobs it does.
- **X-Forwarded-For**: how the app behind still knows who the visitor was.
- Office proxies, and why they break `npm install`.

## A program in the middle

A **proxy** is a program that receives a request, sends it on to someone else, and passes the answer back. Like a receptionist who takes your message, delivers it, and brings back the reply. The two ends each talk only to the proxy.

Which side it works for decides what kind it is.

## Forward proxies: in front of the users

A **forward proxy** sits in front of a group of **users**, usually inside a company or school. Staff's web traffic goes out through it. Organizations use them to:

- block certain websites,
- scan downloads for viruses,
- keep a record of traffic, sometimes for legal reasons.

The websites see the proxy's address, not each employee's. You mostly notice forward proxies when they get in the way. More on that at the end.

## Reverse proxies: in front of the servers

A **reverse proxy** is the mirror image. It sits in front of a website's **servers** and receives requests from the public. Step through one:

<Viz name="reverse-proxy" />

Almost every serious website has one, often **nginx** (said "engine-x"), Caddy, or a cloud provider's equivalent. Its usual jobs:

| Job | What it means |
| --- | --- |
| **One public address** | Visitors see `https://shop.example` and nothing else. Only the proxy is reachable from the internet |
| **Routing** | `/api/...` goes to the API program, `/images/...` to static files, and everything else to the website program |
| **TLS termination** | The proxy holds the certificate and handles HTTPS, so the programs behind it don't have to |
| **Serving static files** | Images, styles and scripts are sent straight from disk, which is very fast |
| **Protection** | Limits on request size and speed, and blocking obvious attacks |

Each of those separate programs behind the proxy is often called a **service**: a program with one job that other programs talk to over the network. Shops, banks and streaming sites are made of many services working together. You'll see a lot more of them in the rest of Stage 2.

<details>
<summary>Quick check: in a reverse proxy setup, which part has the HTTPS certificate?</summary>

Usually the reverse proxy. It decrypts incoming requests (TLS termination) and passes them to the services behind it.
</details>

## Routing in code

A reverse proxy's routing is a list of rules checked in order. In nginx's own settings language it looks roughly like this:

```text
location /api/    { proxy_pass http://localhost:4000/; }
location /images/ { root /var/www; }
location /        { proxy_pass http://localhost:3000; }
```

You don't need to learn nginx's language. The idea is what matters: **match the start of the path, pick a destination, and maybe trim the path**. In the task you'll write the same logic in JavaScript, using two text methods you haven't used yet:

```javascript
"/api/orders".startsWith("/api")   // true: does the text begin with this?
"/api/orders".slice(4)             // "/orders": everything from position 4 onwards
```

- **`.startsWith(text)`** is `true` if the text begins with the given text.
- **`.slice(n)`** gives everything from position `n` to the end. Positions count from 0, as with lists. So `"/api".length` is 4, and slicing 4 characters off the front removes `/api`.

You'll also need JavaScript's way of writing `not`, which is **`!`**: `!existing` is `true` when `existing` is empty or `undefined`. While we're here, `and` is written **`&&`** and `or` is **`||`**. You'll use those two in the next lessons.

## Who really sent this? X-Forwarded-For

There's a catch. Behind a proxy, every connection the app sees comes **from the proxy**. If the app logs visitors' IP addresses, or blocks an abusive one, they all look identical.

So the proxy adds a request header with the original visitor's address:

```text
X-Forwarded-For: 203.0.113.7
```

If the request passes through several proxies, each one adds the address it received the request from, separated by commas: `203.0.113.7, 10.0.0.2`. The first entry is the original visitor, as far as anyone can tell.

<Callout kind="warn" title="Anyone can send that header">
A visitor can write their own `X-Forwarded-For: 1.2.3.4` header. An app should only trust the entry its **own** proxy added, and the app shouldn't be reachable except through that proxy. Otherwise anyone can pretend to be any IP address, and get round IP-based limits.
</Callout>

## Office proxies and npm install

Back to forward proxies, because they cause one of the most common "works at home, fails at work" problems.

**Problem 1: tools don't know the proxy exists.** Browsers pick up Windows' proxy settings. Command-line tools like npm, pip and curl often don't. The standard fix is environment variables they all read:

```powershell
$env:HTTPS_PROXY = "http://proxy.corp.example:8080"
$env:HTTP_PROXY  = "http://proxy.corp.example:8080"
```

**Problem 2: certificate errors.** Some company proxies do **TLS inspection**: they decrypt HTTPS traffic to scan it, then re-encrypt it with the **company's own certificate**. Company laptops are set up so browsers trust that certificate. But Node.js and Python keep their **own** lists of trusted certificate authorities, so they see a certificate signed by an authority they've never heard of, and refuse: "unable to get local issuer certificate".

<Callout kind="warn" title="Don't turn the check off">
AI assistants often suggest `npm config set strict-ssl false` or `verify=False`. That's the mistake from the HTTPS lesson: it accepts **any** certificate, including an attacker's. The right fix is to get the company's root certificate from IT and tell the tool to trust it too. For Node, set the `NODE_EXTRA_CA_CERTS` environment variable to that file's path.
</Callout>

<ConsultantNote>
Reverse proxies show up in almost every architecture diagram you'll review, and they're where many problems hide: an expired certificate, a missing route, or an app trusting X-Forwarded-For from anyone. Office proxies matter when you work on-site: knowing about HTTPS_PROXY and TLS inspection turns a lost morning into a five-minute fix, and stops a client's team from switching security checks off "temporarily".
</ConsultantNote>
