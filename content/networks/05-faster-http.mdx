## In this lesson

The last lesson showed that waiting, not bandwidth, is usually what makes the web slow: every round trip costs time. This lesson covers the two big ways HTTP fights that:

- **Newer versions of HTTP**, which waste fewer round trips: **keep-alive**, **HTTP/2** and **HTTP/3**.
- **Caching**: response headers that let a browser skip a request entirely, or get a tiny "nothing changed" answer.

## Keep-alive: don't hang up between requests

In the earliest HTTP, every request opened a new TCP connection (one round trip for the handshake, plus TLS for HTTPS), sent one request, and closed it. A page with 40 images paid for 40 handshakes.

HTTP/1.1 made **keep-alive** the default: after a response, the connection stays open for the next request. That alone saves a lot of round trips. But HTTP/1.1 still has a limit: on one connection, requests go **one at a time**. The second waits until the first response has fully arrived, like one checkout lane with a queue.

Browsers work around it by opening about **six connections** to each site at once. That's six lanes, but each one still has a queue behind it.

## HTTP/2: many requests at once on one connection

HTTP/2 (2015) changed how the messages travel, without changing what they mean. Methods, paths, headers and status codes are all the same. But:

- Requests and responses are cut into small numbered pieces, and **many of them share one connection at the same time**. A big image and a tiny script no longer queue behind each other. This is called **multiplexing**.
- Headers are **compressed**, because pages send nearly identical headers hundreds of times.

You don't change your code to use HTTP/2. The browser and the server agree on it during the TLS handshake. Most big sites already use it.

## HTTP/3: fixing what TCP can't

HTTP/2 left one problem behind. All those requests share one **TCP** connection, and TCP delivers everything strictly in order. When **one** packet is lost, TCP holds back **everything** after it until the resend arrives, even pieces belonging to completely different files. One straggler blocks the whole queue. That's called **head-of-line blocking**.

On a good connection it rarely matters. On a phone moving between cell towers, or on busy Wi-Fi, it hurts.

**HTTP/3** (2022) moves off TCP onto a new protocol called **QUIC**, built on top of **UDP**. QUIC does its own numbering and resending, like TCP, but **separately for each request**, so a lost packet only delays the one file it belongs to. It also combines the connection and encryption handshakes, saving another round trip.

| Version | Runs on | Requests per connection | Main win |
| --- | --- | --- | --- |
| HTTP/1.1 | TCP | One at a time | Keep-alive: reuse the connection |
| HTTP/2 | TCP | Many at once | Multiplexing and compressed headers |
| HTTP/3 | QUIC over UDP | Many at once, independent | No head-of-line blocking, faster setup |

You can see which version each request used in the browser's **Network tab**: right-click the column headings and turn on **Protocol**. `h2` is HTTP/2 and `h3` is HTTP/3.

<details>
<summary>Quick check: why did HTTP/3 move from TCP to UDP?</summary>

Because TCP delivers everything strictly in order, so one lost packet holds up all the requests sharing the connection. QUIC, built on UDP, handles each request separately.
</details>

## Caching: the fastest request is the one you don't send

Every version above makes requests cheaper. **Caching** avoids them altogether. When a browser receives a file, it can keep a copy in its **browser cache** on your disk. Next time the page needs that file, it may use the copy. The server decides whether that's allowed, with response headers.

### Cache-Control

The **Cache-Control** response header sets the rules. Its parts are separated by commas:

| Value | Meaning |
| --- | --- |
| `max-age=3600` | You may reuse this copy for 3,600 seconds (an hour) **without asking** |
| `no-cache` | You may keep a copy, but **check with the server** before every reuse. The name is misleading |
| `no-store` | Don't keep a copy at all. For private things like bank statements |
| `public` / `private` | Shared caches, like a CDN, may / may not keep a copy. `private` means only the user's own browser. More on this in *CDNs* |

So `Cache-Control: public, max-age=86400` on a logo means: anyone may keep this for a day.

### ETags and 304 Not Modified

What happens when `max-age` runs out, or with `no-cache`? The browser doesn't have to download the whole file again. It can **revalidate**: ask "has this changed?"

1. The first response included an **ETag** header: a label for this exact version, like `ETag: "catalog-v1"`.
2. The browser sends the label back in an **If-None-Match** request header: "send it only if it's no longer `catalog-v1`".
3. If nothing changed, the server answers **304 Not Modified**, with **no body**. A few hundred bytes instead of the whole file.
4. If it did change, the server sends `200 OK` with the new version and a new ETag.

A 304 still costs a round trip, but it saves the download. You'll earn one in the task.

<details>
<summary>Quick check: what does a browser send to ask "has this changed since version v7?"</summary>

An `If-None-Match: "v7"` request header. If it still matches, the server answers 304 Not Modified.
</details>

## Seeing headers with curl

Two curl options help here:

- `-D first-headers.txt` saves the response **headers** to a file, separately from the body. (`-i` from the last lesson mixes them into the body instead.)
- `-w "%{http_version}"` prints a detail about the request once it's finished. Here, which HTTP version was used.

One PowerShell detail: a real ETag includes double quotes, like `"catalog-v1"`, and PowerShell makes passing quotes to curl awkward. So in the task you'll send `If-None-Match: catalog-v1` without them, and Groundwork's practice API accepts that.

## Python: cleaning up text with .strip()

In the Python task you'll split a Cache-Control header on commas. `"public, max-age=60".split(",")` gives `["public", " max-age=60"]`. Notice the space at the start of the second part. **`.strip()`** removes spaces from both ends of a piece of text: `" max-age=60".strip()` gives `"max-age=60"`. You'll use it on every part before comparing.

<ConsultantNote>
Caching is often the cheapest performance fix there is, and it's frequently set up wrong. Long `max-age` on files that change means users see old versions. `no-store` on everything means every visit downloads everything again. A quick look at a client's headers in the Network tab often finds an easy win, and occasionally a privacy bug, like a personal page cached where other people can see it.
</ConsultantNote>
