## In this lesson

Big websites don't run on one computer. They run on many identical ones behind a single address. This lesson covers:

- **Vertical** and **horizontal** scaling: a bigger server, or more servers.
- **Load balancers**, and the two common ways they share out requests: **round robin** and **least connections**.
- **Health checks**: how a load balancer notices a sick server.
- Why the servers behind it should be **stateless**, and what **sticky sessions** are.
- **Single points of failure**: the part you forgot to double up.

## A bigger server, or more servers?

When one server can't keep up, there are two ways to grow:

- **Vertical scaling** means a **bigger** machine: more processor cores, more memory. It's simple, because nothing about the software changes. But there's a ceiling (the biggest machine available), the price rises steeply near the top, and it's still **one** machine. If it fails, everything is down.
- **Horizontal scaling** means **more** machines, each running an identical copy of the app. It can keep growing by adding machines, and if one fails, the others carry on. The catch is that something has to share requests between them, and the app has to cope with any request landing on any machine.

Small sites usually start vertical, and that's fine. Horizontal scaling is how almost everything large is built.

## The load balancer

A **load balancer** is a reverse proxy whose main job is **sharing requests between several servers**. DNS points the site's name at the load balancer, and visitors never see the servers behind it. Step through one:

### How it chooses

The two most common strategies:

- **Round robin**: each server in turn, 1, 2, 3, 1, 2, 3… Simple and fair when every request takes about the same time.
- **Least connections**: send each request to whichever server is handling the **fewest** requests right now. Better when some requests are slow (a big report) and others are quick (a product page), because a server stuck on slow ones naturally gets fewer new ones.

You'll write both in the task.

### A counting loop in JavaScript

Round robin needs a loop that runs a set number of times, rather than once per item. JavaScript has a classic loop for that:

```javascript
for (let tries = 0; tries < servers.length; tries++) {
  // runs with tries = 0, 1, 2, … up to servers.length - 1
}
```

Read the three parts in the brackets, separated by semicolons:

1. `let tries = 0` runs once, at the start.
2. `tries < servers.length` is checked before each round. When it's false, the loop stops.
3. `tries++` runs after each round. `++` means "add one".

It's the same as Python's `for tries in range(len(servers)):`. You'll see it constantly in older JavaScript code.

## Health checks

A load balancer must not send visitors to a server that's broken. So every few seconds, it sends each server a **health check**: usually a tiny request like `GET /health`.

- A quick `200 OK` means "healthy, keep sending me traffic".
- An error, or no answer, a few times in a row means "take me out". The load balancer stops sending it anything.
- When it starts passing again, it's quietly added back.

A good `/health` checks the things the server can't work without, like whether it can reach the database, and answers fast. Visitors notice nothing when one server dies, which is the point.

<details>
<summary>Quick check: what does a load balancer do with a server that fails its health checks?</summary>

It stops sending it requests until it passes again. The other servers take its share.
</details>

## The session problem

Here's the trap that catches nearly everyone the first time. In *Cookies and sessions*, the server stored each logged-in user's session. Suppose each app server keeps sessions **in its own memory**:

1. Ada logs in. The load balancer sends her to server 1, which creates her session.
2. Her next click goes to server 2. Server 2 has never heard of her session. She's logged out.

There are two fixes:

- **Sticky sessions**: the load balancer remembers which server each user went to (usually with a cookie of its own) and always sends them back there. It's quick to switch on, but load gets uneven, and when that server dies, its users lose their sessions anyway.
- **Stateless servers**: the servers keep **nothing** about users in their own memory. Sessions go in a **shared store** that every server can read, often a fast in-memory database called Redis. Any server can handle any request, and servers can be added, removed or restarted freely.

Stateless servers are the proper answer. "Keep app servers stateless" is one of the most repeated rules in system design.

## Single points of failure

You added a load balancer and three servers, so a server can die without the site going down. But what if the **load balancer** dies? Or the one database? A **single point of failure** is any part that takes everything down when it fails, because there's only one of it.

Removing them means doubling up: two load balancers sharing one address, a standby copy of the database that takes over automatically, servers in two separate data centers. Each one costs money, so the real question for a client is **which failures they can afford**. That's a big theme in Stage 4.

Cloud providers sell load balancers as a service, which are themselves built from many machines, so you don't run them yourself. Examples are AWS's Application Load Balancer and Azure Load Balancer.

<ConsultantNote>
When a client says "we need to scale", ask what's actually slow, and how much traffic they expect. Many apps never outgrow one well-sized server, and vertical scaling is far simpler. When they do need horizontal scaling, the work isn't the load balancer, which is a few clicks in any cloud. It's making the app stateless. That's a real code change, and you should spot it before anyone promises a deadline.
</ConsultantNote>
