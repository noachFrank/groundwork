## In this lesson

In the HTTP lesson you learned two things that seem to contradict each other: HTTP is **stateless** (every request stands alone), and yet websites keep you logged in. This lesson explains how:

- How a server puts a cookie in your browser with **Set-Cookie**.
- **Sessions**: the server's memory of who's logged in, found by a random **session ID**.
- The cookie settings that keep a session safe: **HttpOnly**, **Secure**, **SameSite** and expiry.
- **Third-party cookies** and tracking.
- **Session hijacking**: what a stolen cookie means, and how to limit the damage.

## The problem

Picture a shop with a terrible memory. You walk up to the counter and say "I'm Ada, here's my password." The assistant checks, nods, and you ask for your order history. They stare at you blankly: "Who are you?" Every request is a stranger.

That's HTTP. The server answers each request and forgets it. To stay logged in, every request after the first has to carry **proof of who you are**. Sending your password every time would be risky and clumsy. Instead, the server gives you something like a cloakroom ticket.

## Set-Cookie: the server hands you a ticket

When you log in successfully, the server's response includes a **Set-Cookie** header:

```text
HTTP/1.1 200 OK
Set-Cookie: session=7f3a9c41e0b2d8a6; Path=/; HttpOnly; Secure; SameSite=Lax; Max-Age=3600
```

The browser stores that cookie. From then on, every request it sends to that site carries it back, automatically, in a **Cookie** request header:

```text
GET /account HTTP/1.1
Host: shop.example
Cookie: session=7f3a9c41e0b2d8a6
```

The browser's store of cookies is often called its **cookie jar**. You can see a site's cookies in the developer tools (F12), under **Application** (Chrome and Edge) or **Storage** (Firefox).

## Sessions: the server's memory

The cookie's value, `7f3a9c41e0b2d8a6`, means nothing by itself. It's a **session ID**: a long random value, like a cloakroom ticket number. On the server, a **session** is stored under that ID: which user it is, when they logged in, when it expires. It's often kept in a database or a fast in-memory store.

So every request goes like this:

1. The browser sends `Cookie: session=7f3a…`.
2. The server looks up session `7f3a…` and finds "this is Ada, logged in until 15:30".
3. It answers as Ada.

The ID has to be long and random, so nobody can guess someone else's. And the real details stay on the server, where users can't change them. The flaw task shows what goes wrong when they don't.

<details>
<summary>Quick check: where is the information that says "this is Ada" actually stored?</summary>

On the server, in the session. The browser only holds the random session ID that points to it.
</details>

## Doing it with curl

curl doesn't keep cookies unless you ask it to. Two options turn it into a tiny browser:

| Option | Meaning |
| --- | --- |
| `-c cookies.txt` | After the request, save any cookies the server set into this file (the cookie jar) |
| `-b cookies.txt` | Send the cookies from this file with the request |
| `-d "a=1&b=2"` | Send this data as a POST request, the way an HTML form would |
| `-i` | Include the response headers in the output, so you can see Set-Cookie |
| `-X POST` | Use the POST method, even with no data to send |

In the task you'll ask "who am I?", log in, look inside the jar, ask again with the cookie, then log out and watch the server forget you.

## The settings that keep cookies safe

The extra parts after the value in Set-Cookie aren't decoration. Each one closes a door attackers use:

| Setting | What it does | Why it matters |
| --- | --- | --- |
| **HttpOnly** | JavaScript on the page can't read the cookie | If an attacker manages to sneak a script onto the page, it still can't steal the session |
| **Secure** | Only sent over HTTPS | The cookie never travels unencrypted, where someone on the café Wi-Fi could read it |
| **SameSite=Lax** (or Strict) | Not sent when another website starts the request | Stops other sites from making your browser do things on a site you're logged into |
| **Max-Age** / **Expires** | When the browser should delete it | Without one, the cookie lasts until the browser closes. Sessions should also expire on the server |

A login cookie should have **all of them**. In the CORS lesson you saw that letting another origin send cookies is a big decision. SameSite is the browser's own protection on the same theme.

<Callout kind="warn" title="Logging out has to happen on the server">
Clearing the cookie in the browser isn't enough. If someone copied the session ID earlier, it still works until the **server** deletes the session. A proper logout deletes the session on the server. That's what the practice API's /logout does in the task.
</Callout>

## Session hijacking

The session ID is effectively a key to the account. Anyone who gets a copy can send it and **be** that user, with no password needed, until the session ends. This is **session hijacking**.

How cookies get stolen, and the defense against each:

- **Read off an unencrypted connection** → Secure, and HTTPS everywhere.
- **Read by a malicious script on the page** → HttpOnly.
- **Copied from a shared or stolen computer** → sessions that expire, and a "log out everywhere" button that deletes all of a user's sessions.

## Third-party cookies and tracking

A cookie belongs to the site that set it. A **first-party cookie** is set by the site in your address bar. A **third-party cookie** is set by a different site whose content is embedded in the page, typically an advertising network whose code appears on thousands of sites. Because your browser sends that network's cookie on every one of those sites, the network can follow you around the web.

Browsers have been cutting this off, and privacy laws like the EU's GDPR require consent for tracking cookies. That's what those cookie banners are about. Cookies a site needs just to work, like the login session, are generally treated differently from tracking.

## Cookies or tokens?

You'll also see logins that don't use a session cookie. Instead, the server hands back a **token**, and JavaScript sends it in a header with each request. That's common for mobile apps and for APIs, and you'll meet tokens properly in *Proving who's calling*. For ordinary websites, a session cookie with all the settings above is still the simplest safe choice.

<ConsultantNote>
"How do logins work in your app?" is one of the first questions in any security review. Look at the session cookie in the browser's developer tools: is it HttpOnly, Secure and SameSite? Does it expire? Does logging out actually end the session on the server? Those checks take five minutes, and they're among the most common findings in real audits.
</ConsultantNote>
