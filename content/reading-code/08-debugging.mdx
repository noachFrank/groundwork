## The worst bugs don't crash

A crash at least tells you where to look: there's a traceback pointing at a line. The bugs that cost clients money usually **don't** crash. They give a slightly wrong price, skip a customer, or fail only for some people. Everything looks fine, and the program happily carries on with the wrong answer.

Finding those takes a method, not luck.

## The method

1. **Reproduce it.** Find a small example where you know the right answer, and can make the wrong one happen every time. If you can't reproduce a bug, you can't confirm you've fixed it.
2. **Narrow it down.** Which part of the program is it in? Cut the problem in half: is the data right going **into** this function? Is it right coming **out**? Keep halving until you've cornered it.
3. **Look at the real values.** Don't assume what a variable holds. Check. Add `print()` calls, or use a debugger, and see.
4. **Fix the cause**, not the symptom. If page 1 is wrong because of a calculation, fix the calculation, don't add a special case for page 1.
5. **Check it's fixed.** Run the same reproduction. Then check you haven't broken anything nearby, and look for the same mistake elsewhere in the code.

## Print debugging

The simplest tool is still one of the best. Add temporary `print()` lines to see inside a function while it runs:

```python
def get_page(items, page_number, per_page):
    start = page_number * per_page
    end = start + per_page
    print("page", page_number, "start", start, "end", end)   # temporary
    return items[start:end]
```

`print` can take several values separated by commas, and shows them with spaces in between. Running `get_page(products, 1, 3)` now also prints:

```text
page 1 start 3 end 6
```

Page 1 should obviously start at position 0, the first product. Now you know exactly which line to look at. Remove the extra prints once you've fixed it.

Code editors like VS Code have a proper **debugger**, which pauses the program on a line you choose and lets you look at every variable. It's the same idea, with more power. Print debugging works everywhere, including Groundwork's editor.

## Slicing: a chunk of a list

The exercise uses **slicing**, a way to get part of a list:

```python
items = ["Lamp", "Desk", "Chair", "Shelf", "Rug"]
#          0       1       2        3       4

items[0:3]    # ["Lamp", "Desk", "Chair"]   positions 0, 1, 2
items[3:5]    # ["Shelf", "Rug"]            positions 3, 4
items[3:10]   # ["Shelf", "Rug"]            past the end is fine: you get what's there
```

`items[a:b]` gives the items from position `a` **up to, but not including**, position `b`. That "not including" is the same rule as `range`, and it's deliberate: `items[0:3]` gives exactly 3 items.

<details>
<summary>Quick check: with the list above, what's `items[1:3]`?</summary>

`["Desk", "Chair"]`: positions 1 and 2. Position 3 isn't included.
</details>

### Pages are counted from 1, positions from 0

That mismatch is the heart of the exercise. People say "page 1" for the first page, but the first product is at position 0. Whenever a human-friendly number (starting at 1) meets a list position (starting at 0), watch for off-by-one bugs.

Before you change any code in the exercise, work out by hand what `start` should be for page 1, page 2 and page 3, with 3 per page. Then compare with what the code calculates.

## Useful habits

- **Change one thing at a time.** Otherwise you won't know which change fixed it, or which one broke something else.
- **Ask "what changed?"** A bug that started last Tuesday usually comes from something that changed last Tuesday: new code, an updated package, a new setting. `git log` tells you exactly what changed, and when.
- **Explain it out loud.** Rubber duck debugging, from the first module, works remarkably well.
- **Take a break.** Fresh eyes find bugs that tired ones stare straight past.

<Callout title="Asking AI to debug">
AI can be good at spotting bugs, if you give it what you'd give a person: the code, the input, what you expected, and what actually happened. "It doesn't work" gets a guess. "For page 1 I expected Lamp, Desk, Chair but got Shelf, Rug, Clock" usually gets the answer.
</Callout>

## When strange input breaks things

The second task mentions a bug that only hits customers with an apostrophe in their name, like O'Brien. That's a classic. Some code builds commands out of text that people type, and a stray apostrophe or quote mark changes the meaning of the command. Sometimes that's just a crash. Sometimes it lets an attacker sneak in their own commands, a security hole called **injection**. You'll meet it properly in the security part of the course. For now: odd characters breaking things is worth a second look.

<ConsultantNote>
Clients rarely report bugs precisely. "It's broken sometimes" is normal. Turning that into "it fails for surnames with apostrophes since last Tuesday's update" is a valuable skill. It's careful questions plus this method, and it's what makes clients trust you with their systems.
</ConsultantNote>
