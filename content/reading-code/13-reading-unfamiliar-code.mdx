      app.post("/api/checkout", async (req, res) => {
        const { customerId, code, total } = req.body;
        let discount = 0;

        if (code = "WELCOME10") {
          discount = total * 0.1;
        }

        const order = await saveOrder(customerId, total - discount);
        res.json({ orderId: order.id, charged: total - discount });
      });
    flawLines: [5]
    lineNotes:
      "1": Defining a checkout endpoint that waits on async work is normal.
      "2": Reading values from the request body is normal. Though should the server trust a total sent by the browser? Note that for later, but it's not the bug asked about.
      "3": Starting the discount at 0 is right.
      "6": 10% of the total is the right amount, when the discount applies.
      "9": Saving the order after the discount is right.
      "10": Returning the order is fine.
    explanation: |
      `code = "WELCOME10"` uses **one** equals sign, so it **assigns** "WELCOME10" to code instead of comparing. The value of an assignment is the assigned text, which counts as true, so the discount applies to every order. The manual test passed because the tester typed the right code.

      The fix is `if (code === "WELCOME10")`. Tools called **linters** flag this pattern automatically, which is one reason good projects use them.

      And line 2's note is a real second issue: the server takes `total` from the browser, which a user could change. Prices should be worked out on the server. Good reviewers notice both: the bug asked about, and the risk nobody mentioned.

## Most code you read won't be yours

As a consultant, you'll spend far more time reading other people's code than writing your own: client projects, old systems, packages, and more and more often, AI-written code. Reading code well is the core skill. This lesson is about doing it efficiently.

## Finding your way around

Nobody reads a whole codebase. Build a map, then follow one path:

1. **The README.** What is it, and how do you run it? Even a bad README tells you something.
2. **The package list**: `package.json`, `requirements.txt` or similar. It shows the language, the main packages and tools. The `scripts` section tells you how it starts.
3. **Get it running** on your machine, using the setup checklist from the npm lesson. Code you can run is far easier to understand than code you can only read.
4. **Find the entry point**, the file where the program starts (often named in package.json's scripts), and look at the folder structure. Typical folders are `src/` (source code), `routes/` or `api/` (backend request handlers), `components/` (pieces of the frontend), `models/` (descriptions of the data) and `tests/`.
5. **Trace one real feature** from start to finish. For example: the booking form on the page → the request it sends → the backend code that receives it → where the data is saved. Once you've followed one path all the way through, you understand how the whole app is wired.

## Search is your superpower

To find where something happens, **search the whole project** for something you can see:

- Text on the screen: a button label or an error message.
- An address from the browser's address bar.
- A name from an error log.

In VS Code, a popular free code editor, **Ctrl+Shift+F** searches every file at once. Search beats reading every time.

## Reading a backend route

Much backend JavaScript looks like this. It's the code in the task:

```javascript
app.post("/api/checkout", async (req, res) => {
  const { customerId, code, total } = req.body;
  // ... work things out, save the order ...
  res.json({ orderId: order.id, charged: total - discount });
});
```

You can read it with what you know:

- `app.post("/api/checkout", ...)` sets up a **route**: "when a request arrives for the address `/api/checkout`, run this function". (`post` is a kind of request used for sending data. Stage 2 covers the kinds.) `app` is the server, built with a popular package.
- `async (req, res) => { ... }` is an async arrow function. It's given two objects: **`req`**, the **request** that arrived, and **`res`**, the **response** it will send back.
- **`req.body`** is the data the browser sent with the request, already turned from JSON into a JavaScript object.
- `res.json({...})` sends back a response, as JSON.

### Destructuring

The second line uses a shortcut called **destructuring**:

```javascript
const { customerId, code, total } = req.body;
```

That means exactly the same as:

```javascript
const customerId = req.body.customerId;
const code = req.body.code;
const total = req.body.total;
```

It pulls several values out of an object into variables of the same names, in one line. You'll see it everywhere.

<details>
<summary>Quick check: after `const { name, age } = person;`, what's in `name`?</summary>

The same as `person.name`.
</details>

## Reviewing code

Whether a teammate or an AI wrote it, ask:

| Question | What you're looking for |
| --- | --- |
| Does it do what was **asked**? | Not just what the one example tested |
| What about the **edges**? | Empty lists, missing values, exactly-on-the-boundary numbers, odd characters like apostrophes |
| What happens when it **fails**? | Errors swallowed? Network calls that might never answer? |
| Is it **safe**? | Trusting data from the browser, missing permission checks, secrets in code |
| Can someone **read** it? | Names that say what things do, and no surprises |

### Never trust the browser

One safety point deserves its own heading. Anything that comes from the browser, like `req.body`, can be changed by the person using it, with the browser's developer tools or a tool like curl. So a server should never take a **price** or a **total** from the browser and simply believe it. It should work prices out itself, from its own data. Notice this in the task: it's a second problem, beyond the one the question asks about.

### The bugs from this module

You've met these one at a time. Together, they're a checklist of things that slip past a quick test and get caught by a careful reader:

- `>` instead of `>=` (boundary bugs)
- `or` instead of `and`
- A missing `return`, giving None or undefined
- Text instead of numbers ("4.50" + "2.00")
- `=` instead of `===`
- A line indented one level too far, or not far enough

Tools called **linters** read code automatically and flag common mistakes like `=` inside an `if`. Good projects run one on every change.

<Callout title="Reviewing AI-written code">
AI code often looks polished, which makes it easy to trust. Review it like a stranger's: read every line, test the edge cases, and be extra suspicious of anything that "fixes" an error by turning a check off. That's a pattern you've now seen several times.
</Callout>
