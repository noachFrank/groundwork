      });
    flawLines: [5]
    lineNotes:
      "1": Defining a checkout endpoint that waits on async work is normal.
      "2": Reading values from the request body is normal. Though should the server trust a total sent by the browser? Note that for later, but it's not the bug asked about.
      "3": Starting the discount at 0 is right.
      "6": 10% of the total is the right amount, when the discount applies.
      "9": Saving the order after the discount is right.
      "10": Returning the order is fine.
    explanation: |
      `code = "WELCOME10"` uses **one** equals sign, so it **assigns** "WELCOME10" to code instead of comparing. The value of an assignment is the assigned text, which counts as true, so the discount applies to every order. The manual test passed because the tester typed the right code.

      The fix is `if (code === "WELCOME10")`. Tools called **linters** flag this pattern automatically, which is one reason good projects use them.

      And line 2's note is a real second issue: the server takes `total` from the browser, which a user could change. Prices should be worked out on the server. Good reviewers notice both: the bug asked about, and the risk nobody mentioned.

## Most code you read won't be yours

As a consultant, you'll spend far more time reading other people's code than writing your own: client projects, old systems, libraries, and more and more often, AI-written code. Reading code well is the core skill. This lesson is about doing it efficiently.

## Finding your way around

Nobody reads a whole codebase. Build a map, then follow one path:

1. **The README.** What is it, and how do you run it? Even a bad README tells you something.
2. **The package list:** `package.json`, `requirements.txt` or similar. It shows the language, the framework and the major tools. The `scripts` section tells you how it starts.
3. **Get it running** on your machine. Code you can run is far easier to understand than code you can only read.
4. **Find the entry point**, where the program starts, and the folder structure. Typical folders are `src/`, `routes/` or `api/`, `components/`, `models/` and `tests/`.
5. **Trace one real feature** from start to finish. For example: the booking form → the request it sends → the server route → the database. Now you understand how the whole app is wired.

## Search is your superpower

To find where something happens, **search the whole project** for something you can see:

- Text on the screen: a button label or an error message.
- A URL from the browser's address bar or the network tab.
- A name from the database or an error log.

In VS Code, **Ctrl+Shift+F** searches every file at once.

## Reviewing code

Whether a teammate or an AI wrote it, ask:

| Question | What you're looking for |
| --- | --- |
| Does it do what was **asked**? | Not just what the example tested |
| What about the **edges**? | Empty lists, missing values, exactly-on-the-boundary numbers, odd characters like apostrophes |
| What happens when it **fails**? | Errors swallowed? Network calls that might never answer? |
| Is it **safe**? | Trusting data from the browser, missing permission checks, secrets in code |
| Can someone **read** it? | Names that say what things do, and no surprises |

The bugs you've met in this module, like `>` instead of `>=`, `or` instead of `and`, a missing `return`, text instead of numbers, and `=` instead of `===`, are exactly what slips past a quick test and gets caught by a careful reader.

<Callout title="Reviewing AI-written code">
AI code often looks polished, which makes it easy to trust. Review it like a stranger's: read every line, test the edge cases, and be extra suspicious of anything that "fixes" an error by turning a check off. That's a pattern you've now seen several times.
</Callout>
