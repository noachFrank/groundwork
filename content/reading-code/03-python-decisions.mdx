## In this lesson

- How to **compare** values, and get True or False back.
- How to make a program **choose** what to do with `if`, `elif` and `else`.
- How to combine conditions with `and`, `or` and `not`.
- **Boundary bugs**: the `>` versus `>=` mistake that catches everyone, and how testers find them.

You'll write the decisions inside functions, like the ones from the last lesson.

## Programs that choose

So far, every line of your code has run, top to bottom, every time. Most useful programs need to **make decisions**: free shipping or not, logged in or not, in stock or not. Different situations need different lines of code to run.

That's what `if` is for. But first, the program needs a way to ask yes-or-no questions.

## Comparisons: asking yes-or-no questions

A **comparison** checks two values against each other and gives back a bool: `True` or `False`.

| Operator | Means | Example | Result |
| --- | --- | --- | --- |
| `==` | is equal to | `5 == 5` | `True` |
| `!=` | is not equal to | `5 != 3` | `True` |
| `<` | less than | `3 < 5` | `True` |
| `>` | more than | `3 > 5` | `False` |
| `<=` | less than or equal to | `5 <= 5` | `True` |
| `>=` | more than or equal to | `4 >= 5` | `False` |

Comparisons work on text too: `"Ada" == "Ada"` is `True`, and `"ada" == "Ada"` is `False`, because capitals count.

<Callout kind="warn" title="= and ==">
One `=` **stores** a value: `x = 5` puts 5 into x. Two `==` **ask** a question: `x == 5` checks whether x is 5, and gives True or False. Mixing them up is one of the classic mistakes. You'll see a nastier version of it in JavaScript later.
</Callout>

<details>
<summary>Quick check: what does `10 >= 10` give?</summary>

`True`. "More than **or equal to**", and 10 is equal to 10.
</details>

## if: run some lines only when something's true

```python
if order_total >= 50:
    shipping = 0
```

Read it as: "**If** the order total is 50 or more, **then** set shipping to 0."

- `if` is followed by a condition, something that's True or False, then a colon `:`.
- The indented lines below it only run when the condition is `True`. When it's `False`, Python skips them.

That's the same indentation rule you learned with functions: the indented lines **belong to** the line above. An `if` inside a function is indented once more:

```python
def shipping_cost(order_total):
    if order_total >= 50:       # inside the function
        return 0                # inside the if, inside the function
    return 5                    # inside the function, after the if
```

Follow it through for an order of 80: the condition is True, so it returns 0, and the function ends right there. (Remember: `return` ends the function immediately.) For an order of 20: the condition is False, so Python skips the indented `return 0`, carries on, and reaches `return 5`.

## elif and else: more than one path

Often there are several possibilities:

```python
if order_total >= 50:
    shipping = 0
elif order_total >= 20:
    shipping = 2.5
else:
    shipping = 5
```

- `elif` means "else, if…": checked only if everything above it was False.
- `else` catches everything that's left. It has no condition.

Python checks the conditions **from the top** and runs the block under the **first one that's True**. Then it skips the rest. **Only one block ever runs.**

Follow it for 30: is 30 >= 50? No. Is 30 >= 20? Yes, so shipping = 2.5, and the `else` is skipped.

Order matters. If the 20 check came first, an order of 80 would match it first and never reach the 50 check.

<details>
<summary>Quick check: in the example above, what's shipping for an order of 10?</summary>

`5`. Neither condition is True, so the `else` runs.
</details>

## Combining conditions

- `and`: **both** must be True.
- `or`: **at least one** must be True.
- `not`: flips True to False, and False to True.

```python
if password_ok and not account_locked:
    print("Welcome")
```

"If the password is right, and the account is **not** locked."

A bool variable can be a condition all by itself: `if is_international:` means the same as `if is_international == True:`, and reads better.

When you read a combined condition, try it with each combination of True and False. That's how the bug in this lesson's second task shows itself.

## Test the edges

When you read or test a condition, try three kinds of value:

- One clearly inside the range, like 80.
- One clearly outside it, like 20.
- **Exactly the boundary**, like 50, and just either side of it, like 49.99.

The boundary is where `>` versus `>=` bugs hide. "Free shipping on orders of **50 or more**" needs `>=`. With `>`, an order of exactly 50 gets charged, and only a test at exactly 50 catches it. Testers call this **boundary testing**, and these mistakes **boundary bugs**.

<ConsultantNote>
Business rules, like "free shipping over 50", "discount for members", or "managers can approve refunds", end up as `if` statements. When a client says "the system is charging people wrongly", the bug is very often one condition with the wrong operator, or a missing case.
</ConsultantNote>

## Words in this lesson

| Word | Meaning |
| --- | --- |
| **Comparison** | Checking two values, giving True or False: `==`, `!=`, `<`, `>`, `<=`, `>=` |
| **`==` vs `=`** | `==` asks "is it equal?". `=` stores a value. |
| **Condition** | Anything that's True or False, used after `if` |
| **`if`** | Runs its indented lines only when the condition is True |
| **`elif` / `else`** | Further checks, and a catch-all, after an `if`. Only one block runs. |
| **`and` / `or` / `not`** | Both / at least one / the opposite |
| **Boundary bug** | A mistake at the exact edge of a range, like `>` instead of `>=` |
| **Boundary testing** | Testing exactly at the edge, and just either side |
