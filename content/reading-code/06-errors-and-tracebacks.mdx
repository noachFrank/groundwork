## Errors are messages, not failures

Every programmer sees errors constantly, including experienced ones. The difference is that experienced programmers **read** them. Python's errors are unusually helpful once you know where to look.

## Reading a traceback

```text
Traceback (most recent call last):
  File "shop.py", line 12, in <module>
    print(describe("Plums"))
  File "shop.py", line 5, in describe
    count = stock[fruit]
KeyError: 'Plums'
```

**Read it from the bottom up:**

1. **The last line** is the error type and message: `KeyError: 'Plums'`. There's no key "Plums" in the dictionary.
2. **Just above** is where it happened: line 5, in the function `describe`, and the actual code.
3. **Further up** is how the program got there: line 12 called `describe("Plums")`.

"Most recent call last" means the crash is at the bottom.

## The errors you'll see most

| Error | Usually means | Example |
| --- | --- | --- |
| `NameError` | Python doesn't know that name. Often a typo. | `totl` instead of `total` |
| `TypeError` | The wrong kind of value for the operation | `"Total: " + 5` |
| `KeyError` | A dictionary doesn't have that key | `order["phone"]` |
| `IndexError` | A list doesn't have that position | `items[10]` in a 3-item list |
| `AttributeError` | The value doesn't have that method | `None.upper()`, often from a missing return |
| `IndentationError`, `SyntaxError` | Python can't even read the code | A missing colon or bracket |

Notice that `KeyError: 'Plums'` above is a capital-letter problem. The key is "plums". Error messages often show the exact value, which is the clue.

## Handling errors you expect

Some errors aren't bugs. A file might be missing, or a network might be down. For those, `try` and `except` let you handle the problem instead of crashing:

```python
try:
    price = float(user_input)
except ValueError:
    print("Please type a number, like 4.99")
```

Catch **specific** errors you can do something sensible about. Never wrap everything in a bare `except:` to make errors go away, because that hides real bugs.

<Callout kind="warn" title="'It just says error'">
When someone tells you "it gave an error", always ask for the **exact** text, ideally the whole traceback. "An error" could be any of a thousand problems. The full message usually narrows it to one.
</Callout>

<ConsultantNote>
Error messages often reach clients' customers, and sometimes they reveal too much: file paths, database names, even passwords. Real apps show visitors a friendly message and write the full details to a log that only developers see. Checking what errors expose is part of a security review.
</ConsultantNote>
