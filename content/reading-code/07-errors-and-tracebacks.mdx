## Errors are messages, not failures

Every programmer sees errors constantly, including very experienced ones. The difference is that experienced programmers **read** them, calmly, all the way through. Python's errors are unusually helpful once you know where to look.

You've already met a few: TypeError when mixing text and numbers, KeyError for a missing dictionary key, ZeroDivisionError, and IndentationError. This lesson puts them all together.

## Reading a traceback

When a program crashes inside a function, Python prints a **traceback**: a report of the error, plus the trail of function calls that led to it.

```text
Traceback (most recent call last):
  File "shop.py", line 12, in <module>
    print(describe("Plums"))
  File "shop.py", line 5, in describe
    count = stock[fruit]
KeyError: 'Plums'
```

**Read it from the bottom up:**

1. **The last line** is the error type and message: `KeyError: 'Plums'`. There's no key "Plums" in the dictionary. Start here, always.
2. **Just above it** is where it happened: line 5 of shop.py, inside the function `describe`, and a copy of that line of code: `count = stock[fruit]`.
3. **Further up** is how the program got there: line 12, in `<module>`, called `describe("Plums")`. (`<module>` just means "the main part of the file, not inside any function".)

"Most recent call last" is Python reminding you that the crash is at the bottom, and the oldest step at the top.

So this traceback tells a little story: line 12 called describe with "Plums", describe looked up "Plums" in stock on line 5, and there was no such key.

<details>
<summary>Quick check: in a traceback, which line do you read first?</summary>

The last one. It names the error and says what went wrong. Then work upwards to see where, and how the program got there.
</details>

## The errors you'll see most

| Error | Usually means | Example |
| --- | --- | --- |
| `NameError` | Python doesn't know that name. Often a typo, or a variable used outside the function it was made in. | `totl` instead of `total` |
| `TypeError` | The wrong type of value for what you asked | `"Total: " + 5` |
| `KeyError` | A dictionary doesn't have that key | `order["phone"]` |
| `IndexError` | A list doesn't have that position | `items[10]` in a 3-item list |
| `ValueError` | The right type, but a value that makes no sense | `int("hello")` |
| `AttributeError` | That value doesn't have that method | `None.upper()`, often from a missing return |
| `ZeroDivisionError` | Dividing by zero | `total / len(items)` with an empty list |
| `IndentationError`, `SyntaxError` | Python can't even read the code's layout, so nothing runs | A missing colon, bracket or quote |

Error messages often include the **exact value** that caused the trouble. `KeyError: 'Plums'` shows a capital P, but the key in the dictionary is "plums". Keys are case-sensitive, just like Linux file names, so that's the bug.

## Fixing one error at a time

When a program has several bugs, Python stops at the **first** one it hits. So the method is:

1. Run it.
2. Read the last line of the error, and the line number.
3. Fix **that one thing**.
4. Run it again. Python will now get further, and maybe stop at the next bug.
5. Repeat until it runs and the checks pass.

Resist rewriting everything. Small, targeted fixes guided by the message are faster, and you learn exactly what each error meant. The first exercise is built for this.

## Handling errors you expect

Some errors aren't bugs. A user might type "four" where a number should be, or a file might be missing. Crashing isn't the right answer there. `try` and `except` let you **handle** the problem instead:

```python
try:
    price = float(user_input)
except ValueError:
    print("Please type a number, like 4.99")
```

Read it as: "**Try** to run the indented lines. **If** a ValueError happens, don't crash: run the `except` block instead."

- `try:` and `except ...:` both end with colons, and their blocks are indented, just like `if`.
- After `except` you name the **specific** error you expect.
- If no error happens, the `except` block is skipped.

<Callout kind="warn" title="Don't hide bugs">
Catch **specific** errors you can do something sensible about. Never wrap a whole program in a bare `except:`, with no error type, to make errors go away. That hides real bugs: the program carries on with wrong data, and the problem shows up later, somewhere much harder to trace.
</Callout>

<Callout kind="warn" title="'It just says error'">
When someone tells you "it gave an error", always ask for the **exact** text, ideally the whole traceback. "An error" could be any of a thousand problems. The full message usually narrows it to one.
</Callout>

<ConsultantNote>
Error messages often reach clients' customers, and sometimes they reveal too much: file paths, database names, even passwords. Real apps show visitors a friendly message, and write the full details to a log file that only developers see. Checking what errors expose is part of a security review.
</ConsultantNote>
