## Programs that choose

Most useful programs make decisions: free shipping or not, logged in or not, in stock or not. In Python, that's `if`:

```python
if order_total >= 50:
    shipping = 0
elif order_total >= 20:
    shipping = 2.5
else:
    shipping = 5
```

Python checks each condition **from the top** and runs the block under the **first** one that's true. If none are, it runs `else`. Only one block ever runs.

## Indentation is part of the code

The indented lines belong to the `if` above them. Python uses this indentation, usually 4 spaces, instead of brackets. Get it wrong and the program either crashes with an `IndentationError` or, worse, quietly runs lines at the wrong time.

## Comparisons

| Operator | Means |
| --- | --- |
| `==` | is equal to |
| `!=` | is not equal to |
| `<`, `>` | less than, more than |
| `<=`, `>=` | less than or equal to, more than or equal to |

<Callout kind="warn" title="= and ==">
`=` **stores** a value. `==` **asks** whether two values are equal. Mixing them up is one of the classic mistakes, and you'll see a nasty version of it in JavaScript later.
</Callout>

## Combining conditions

- `and`: **both** must be true.
- `or`: **at least one** must be true.
- `not`: flips it.

```python
if password_ok and not account_locked:
    allow_login()
```

## Test the edges

When you read or test a condition, try:

- A value clearly inside the range, like 20.
- A value clearly outside it, like 100.
- **Exactly the boundary**, like 50, and just either side of it, like 49.99.

The boundary is where `>` versus `>=` bugs hide. Testers call this **boundary testing**.

<ConsultantNote>
Business rules, like "free shipping over 50", "discount for members", or "managers can approve refunds", end up as `if` statements. When a client says "the system is charging people wrongly", the bug is very often one condition with the wrong operator or a missing case.
</ConsultantNote>
