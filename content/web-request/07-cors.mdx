## Why does this rule exist?

Imagine you're logged in to your bank in one tab, and you open a shady site in another. Without any rule, that site's JavaScript could call your bank's API and read the answer, using your login, and you'd never know.

Browsers stop this with the **same-origin policy**: by default, a page can only read responses from its own **origin**.

An origin is three things together:

```
https://shop.example:443
scheme  host         port
```

Change any one of them and it's a different origin. `http://localhost:4311` and `http://localhost:4312` are different origins, even on the same computer.

## CORS is the permission slip

Often, cross-origin calls are exactly what you want, like when your site's frontend calls your API. **CORS** (Cross-Origin Resource Sharing) lets a server say who's allowed, with a response header:

```
Access-Control-Allow-Origin: https://shop.example
```

## The confusing part

Three things trip up nearly everyone:

1. **The browser enforces it, not the server.** The server answers normally, then the browser withholds the answer from the page.
2. **Postman and curl don't care.** They aren't browsers, so "it works in Postman" tells you the API is fine, and nothing more.
3. **The fix is on the server.** Nothing you put in the page can grant permission. If it could, the rule would be pointless.

## Preflights

For anything beyond a simple request, like one that sends JSON, the browser first sends a small **preflight**: an `OPTIONS` request that asks "may I send this?" You can trigger one in the lab with the Send JSON button, then watch for it in the log.

## Fixing it well

| Approach | When |
| --- | --- |
| Allow your specific origin | The usual right answer |
| Keep a short list of allowed origins | When you have several sites |
| Allow `*` (any origin) | Only for public data with no login, like an open dataset |
| Call the API from your own server | When you don't control the API, or it needs a secret key |

<ConsultantNote>
CORS errors look alarming and get misdiagnosed as "the API is broken" all the time. A calm "let's try that with curl" can save a client from a needless project. And when you review AI-written code, treat wildcard origins as a thing to question.
</ConsultantNote>
