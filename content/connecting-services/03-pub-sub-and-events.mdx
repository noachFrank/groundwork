        if (!broker.topics[topic]) {
          broker.topics[topic] = [];

        if (!existing) {
          broker.topics[topic].push({ name: name, inbox: [] });

        if (!subscribers) {

        return subscribers.length;

        const subscribers = broker.topics[topic] ?? [];

        if (!found) {

## In this lesson

A queue shares work out: each message goes to **one** worker. Often, though, one thing that happens matters to **many** parts of a system. This lesson covers how that's done:

- **Publish/subscribe**: **topics**, **subscribers** and **fan-out**.
- **Events versus commands**.
- **Loose coupling**: why it's the big win.
- **Eventual consistency** and harder debugging: the costs.
- **Event-driven architecture**, and **Kafka**'s replayable log.

## One event, many listeners

Picture the order service from the Predict question. After saving an order, it could call the email service, then the stock service, then analytics, then loyalty points, one after another. That works, but:

- If analytics is slow, every order waits for it.
- If loyalty is down, does the order fail?
- Adding a fifth reaction means changing, testing and redeploying the order service, for something it doesn't care about.

**Publish/subscribe** ("pub/sub") turns it around. The order service **publishes** one **event**, "order.placed", to a **topic**: a named channel. Any service that cares has **subscribed** to that topic, and each gets **its own copy**. Step through it:

<Viz name="pub-sub" />

Sending one event to many subscribers is called **fan-out**. The order service doesn't know who's listening, and doesn't wait for any of them.

<details>
<summary>Quick check: how is a topic different from the queues in the last lesson?</summary>

On a queue, each message goes to one worker, which shares out the work. On a topic, every subscriber gets its own copy, which spreads the news.
</details>

## Events and commands

There are two kinds of message, and the difference shapes a whole design:

| | Event | Command |
| --- | --- | --- |
| Example | `OrderPlaced`, `PaymentFailed` | `SendReceiptEmail`, `ReduceStock` |
| Says | **What happened**, in the past tense | **What to do** |
| Sent to | Anyone who's interested | One specific service |
| The sender | Doesn't care who reacts | Expects it to get done |

Pub/sub carries events. Queues often carry commands. Naming events in the past tense ("order **placed**", not "place order") keeps the difference clear, and it's a useful habit when reading or designing systems. Webhooks, from earlier in this module, are events sent between companies.

## Loose coupling: the big win

When the publisher doesn't know its subscribers, the parts are **loosely coupled**: each can change without the others changing.

- **Add a reaction** (a "thank you" text message): add a subscriber. The order service is untouched.
- **A subscriber fails**: the others carry on, and in a good setup, its events **wait** until it's back (often each subscriber has its own queue fed by the topic). It catches up.
- **Different teams** can own different subscribers and release them independently.

A design built mainly around services publishing and reacting to events like this is called **event-driven architecture**.

## The costs: be honest about them

Event-driven design isn't free, and consultants earn their keep by naming the costs:

- **Eventual consistency.** For a moment after an order is placed, the order exists but stock hasn't been reduced and the email hasn't gone. The parts **agree eventually**, not instantly. Usually that's fine, but not always. If two customers buy the last tent in the same second, something must decide who gets it.
- **Harder to follow.** With direct calls, you can read one function to see what happens. With events, one order sets off reactions in several services at different moments. Debugging means good logs, a shared id carried through every event, and tracing tools. You'll meet those in Stage 3's lessons on seeing inside production.
- **Duplicates.** Like queues and webhooks, pub/sub is usually at-least-once, so every subscriber must cope with seeing an event twice.

A useful rule: use events where **many** parts react to one thing, or where a slow part must never hold up an important one. Don't turn every simple function call into an event.

## Kafka: events as a log

Most brokers deliver an event and then forget it. **Apache Kafka** is different: it keeps every event in a long-lived, ordered **log**, for days or forever. Each subscriber keeps its own place in the log and reads at its own pace. That makes things possible that ordinary pub/sub can't do:

- **Replay**: a new service can read the whole history of events and build its data from scratch.
- **Recovery**: after a bug, rewind and process events again.

Kafka is powerful and widely used at large companies, and it's also a serious system to run. Managed services include Amazon MSK and Confluent. For smaller needs, simpler managed pub/sub services are common: Amazon SNS and EventBridge, Azure Event Grid and Service Bus topics, and Google Cloud Pub/Sub.

## The task: a tiny broker

In the JavaScript task you'll build the heart of a broker: topics, each with a list of subscribers, and each subscriber with its own **inbox** of events. You'll see fan-out, separate topics, and why a subscriber that joins late only sees events from then on, which is exactly why Kafka's replayable log is valuable.

<ConsultantNote>
"Should we go event-driven?" comes up in many architecture conversations, often because it sounds modern. Good answers are specific: which events, which subscribers, what happens when one is down, how a duplicate is handled, and how someone will trace a single order through the system at 2am. If those questions don't have answers yet, a few direct API calls might be the better design for now.
</ConsultantNote>
