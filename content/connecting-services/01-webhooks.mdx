## In this lesson

## Turning polling around

In *Live updates* you saw HTTP's rule: the client asks, then the server answers. A server can't start a conversation with a browser. But a server **can** start a conversation with **another server**, because a server can send requests too.

That's a **webhook**. Instead of your shop asking the payment company "has it been paid yet?" every few seconds, you give the payment company an address on **your** server. When a payment succeeds, **it** sends **you** an HTTP request. One request, at exactly the right moment, and nothing wasted.

Step through it:

Stripe, PayPal, GitHub, Shopify, Twilio, Slack and most online services send webhooks. "Does it support webhooks?" is a standard question when evaluating a vendor.

## What arrives

You register a **webhook endpoint**: an address on your server, like `https://shop.example/webhooks/payments`. When something happens, the sender POSTs to it:

```text
POST /webhooks/payments HTTP/1.1
Content-Type: application/json
X-Signature: sha256=8f2b6c…

{"id": "evt_0042", "type": "payment.succeeded", "created": "2026-11-11T14:03:00Z",
 "data": {"order_id": 501, "amount": 3500}}
```

The JSON body is the **event payload**. Most senders include:

- an **`id`** for the event, unique and never reused,
- a **`type`**, like `payment.succeeded` or `order.created`, so one endpoint can handle many kinds,
- **when** it happened, and the **data** itself.

The practice API's test webhook looks just like this, with its signature in an `X-Groundwork-Signature` header.

## Rule 1: answer fast

The sender waits a few seconds for your answer. Any **2xx** status means "got it". Anything else, or no answer in time, counts as a **failure**.

So a handler should do the minimum: check the signature, **save** the event somewhere safe, answer `200`, and do any slow work, like sending emails or generating invoices, **afterwards**. The next lesson, on message queues, is the usual way to do "afterwards".

## Rule 2: expect retries, and skip duplicates

When a delivery fails, senders **retry**, often for hours or days, with longer gaps each time. That's good: a brief outage on your side doesn't lose events. But it has a consequence. If your server **did** get the event but answered too slowly, the sender counts it as a failure and sends it **again**. The same event can arrive twice, or more.

So your handler must cope with **duplicates**. The standard way: **remember the ids of events you've handled, and skip any id you've already seen**. A repeated "payment succeeded" must never ship an order twice. This is the "idempotent" idea from *Designing REST APIs*, applied to your own handler: processing an event twice should have the same effect as processing it once.

In the terminal task you'll send the same event twice on purpose, and see two identical ids arrive.

## Rule 3: check the signature

Your webhook endpoint is a **public address**. Anyone can send a POST to it, including someone sending a fake `payment.succeeded` to get free goods. How do you know a request really came from the payment company?

When you set up the webhook, the sender gives you a **signing secret** that only the two of you know. For each delivery, the sender computes an **HMAC** of the body using that secret. An HMAC is a short fingerprint that can only be produced by someone who has the secret, and that changes completely if even one character of the body changes. It's sent in a header.

Your handler computes the same HMAC with **its** copy of the secret and compares them:

- **They match**: the request came from someone with the secret, and the body wasn't changed on the way.
- **They don't**: refuse it, with a `401`, and don't act on it.

In Python, the standard library does the work:

```python
import hashlib
import hmac

SECRET = "whsec_practice"   # in real code: from an environment variable

expected = "sha256=" + hmac.new(SECRET.encode(), body.encode(), hashlib.sha256).hexdigest()
ok = hmac.compare_digest(expected, header)
```

- **`hmac.new(key, message, hashlib.sha256)`** computes the HMAC with the SHA-256 method. `.hexdigest()` gives it as text, in hexadecimal (digits and the letters a to f).
- **`.encode()`** turns text into **bytes**, the raw form that cryptography functions work on. `"abc".encode()` gives `b"abc"`.
- **`hmac.compare_digest(a, b)`** compares two values in a way that takes the same time whether they differ early or late, so an attacker can't guess the signature one character at a time by measuring. Use it instead of `==` for secrets.

The signing secret is a **secret** like any other: keep it in an environment variable, never in code or Git.

## A receiver in ten lines

In the terminal task you'll write this webhook receiver, using only Node's built-in **`http`** module, as in *What "npm run dev" actually does*:

```javascript
const http = require("http");
const fs = require("fs");

http.createServer((req, res) => {
  let body = "";
  req.on("data", (chunk) => { body += chunk; });
  req.on("end", () => {
    const signature = req.headers["x-groundwork-signature"];
    fs.appendFileSync("received.txt", signature + " " + body + "\n");
    console.log("Webhook arrived:", body);
    res.end("thanks");
  });
}).listen(4398, "127.0.0.1", () => console.log("Waiting for webhooks on http://localhost:4398/hook"));
```

Line by line:

- `require("http")` and `require("fs")` load Node's built-in modules for servers and files.
- **`http.createServer((req, res) => { … })`** makes a server. The arrow function runs for **every** request that arrives, with the request (`req`) and the response you'll send (`res`).
- A request's body can arrive in pieces. `req.on("data", …)` runs for each piece, and adds it to `body`. `req.on("end", …)` runs once it has all arrived.
- `req.headers["x-groundwork-signature"]` reads a header. Node gives header names in lowercase.
- `fs.appendFileSync` adds a line to `received.txt` (creating it the first time), so you have a record.
- `res.end("thanks")` sends the answer. With no status set, it's `200 OK`.
- `.listen(4398, "127.0.0.1", …)` starts listening on port 4398, on this computer only, and prints a message once it's ready.

This receiver records everything without checking signatures, which is fine for seeing what arrives. The Python task adds the checks a real one needs.

## Testing webhooks from real services

A real service on the internet can't reach `localhost` on your laptop. To test with one, developers use a **tunnel tool**, like ngrok, Cloudflare Tunnel or a provider's own command-line tool, which gives your local server a temporary public address and forwards requests to it. Here, Groundwork's practice API plays the sender on your own computer, so no tunnel is needed.

<ConsultantNote>
Webhook handlers are among the most common sources of quiet, expensive bugs: duplicate orders from retries, missed events from slow handlers, and forged "payment succeeded" requests to endpoints that never check signatures. Reviewing one is quick. Does it verify the signature, answer fast, skip duplicate ids, and alert someone when deliveries fail? Those four questions are worth asking about every integration a client has.
</ConsultantNote>
