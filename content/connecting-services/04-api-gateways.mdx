    type: javascript
    title: Write the heart of an API gateway
    instructions: |
      You'll use: objects, a `for...of` loop, `.startsWith()` (from *Proxies*) and `??` (from *JavaScript: arrays, objects and arrow functions*).

      `gateway(request, keys, counts, limit, routes)` handles one request like `{ path: "/orders/7", apiKey: "key-mobile" }`. It returns an object saying what to do, checking in this order:

      1. If `request.apiKey` isn't one of the keys in `keys` (an object from key to client name), return `{ status: 401 }`.
      2. Add one to that client's count in `counts` (an object from client name to number, starting at 0). If the new count is more than `limit`, return `{ status: 429 }`.
      3. Find the first route whose `prefix` the path starts with, and return `{ status: "forward", to: route.target + request.path, client: <client name> }`.
      4. If no route matches, return `{ status: 404 }`.
    starter: |
      const keys = { "key-mobile": "mobile-app", "key-partner": "partner-co" };
      const routes = [
        { prefix: "/orders", target: "http://orders-service" },
        { prefix: "/accounts", target: "http://accounts-service" },
      ];

      function gateway(request, keys, counts, limit, routes) {
        // 1. const client = keys[request.apiKey];  no client? return { status: 401 }
        // 2. counts[client] = (counts[client] ?? 0) + 1;  over the limit? return { status: 429 }
        // 3. find a matching route, and forward
        // 4. otherwise 404
        return { status: "forward" };
      }

      const counts = {};
      console.log(gateway({ path: "/orders/7", apiKey: "key-mobile" }, keys, counts, 3, routes));
      console.log(gateway({ path: "/orders/7", apiKey: "stolen" }, keys, counts, 3, routes));
    tests:
      - name: a good request is forwarded to the right service
        code: |
          const got = gateway({ path: "/orders/7", apiKey: "key-mobile" }, keys, {}, 3, routes);
          assert(got.status === "forward" && got.to === "http://orders-service/orders/7" && got.client === "mobile-app", "Got " + JSON.stringify(got));
      - name: an unknown key gets 401
        code: |
          const got = gateway({ path: "/orders/7", apiKey: "stolen" }, keys, {}, 3, routes);
          assert(got.status === 401, "Got " + JSON.stringify(got));
      - name: going over the limit gets 429
        code: |
          const counts = {};
          const r = { path: "/accounts/1", apiKey: "key-partner" };
          const results = [gateway(r, keys, counts, 2, routes), gateway(r, keys, counts, 2, routes), gateway(r, keys, counts, 2, routes)];
          assert(results[0].status === "forward" && results[1].status === "forward", "The first two are within the limit of 2.");
          assert(results[2].status === 429, "The third is over the limit. Got " + JSON.stringify(results[2]));
      - name: each client has its own count
        code: |
          const counts = {};
          gateway({ path: "/orders/1", apiKey: "key-mobile" }, keys, counts, 1, routes);
          const other = gateway({ path: "/orders/1", apiKey: "key-partner" }, keys, counts, 1, routes);
          assert(other.status === "forward", "partner-co hasn't used its limit yet, even though mobile-app has.");
          assert(counts["mobile-app"] === 1 && counts["partner-co"] === 1, "counts should be per client: " + JSON.stringify(counts));

        code: |
          const counts = {};
          gateway({ path: "/orders/1", apiKey: "nope" }, keys, counts, 1, routes);
          assert(Object.keys(counts).length === 0, "Refuse unknown keys before counting anything.");
      - name: no matching route gets 404
        code: |
          const got = gateway({ path: "/admin", apiKey: "key-mobile" }, keys, {}, 3, routes);
          assert(got.status === 404, "Got " + JSON.stringify(got));
    solution: |
      const keys = { "key-mobile": "mobile-app", "key-partner": "partner-co" };
      const routes = [
        { prefix: "/orders", target: "http://orders-service" },
        { prefix: "/accounts", target: "http://accounts-service" },
      ];

      function gateway(request, keys, counts, limit, routes) {
        const client = keys[request.apiKey];
        if (!client) {
          return { status: 401 };
        }
        counts[client] = (counts[client] ?? 0) + 1;
        if (counts[client] > limit) {
          return { status: 429 };
        }
        for (const route of routes) {
          if (request.path.startsWith(route.prefix)) {
            return { status: "forward", to: route.target + request.path, client: client };
          }
        }
        return { status: 404 };
      }
    wrong: |
      const keys = { "key-mobile": "mobile-app", "key-partner": "partner-co" };
      const routes = [
        { prefix: "/orders", target: "http://orders-service" },
        { prefix: "/accounts", target: "http://accounts-service" },
      ];

      function gateway(request, keys, counts, limit, routes) {
        counts.all = (counts.all ?? 0) + 1;
        if (counts.all > limit) {
          return { status: 429 };
        }
        for (const route of routes) {
          if (request.path.startsWith(route.prefix)) {
            return { status: "forward", to: route.target + request.path, client: keys[request.apiKey] };
          }
        }
        return { status: 404 };

## In this lesson

The last few lessons have been about services talking to each other behind the scenes. This one is about the front door, where outside requests come in:

- What an **API gateway** is, and the **jobs** it does once for everyone.
- How it differs from a **reverse proxy** and a **load balancer**.
- **Backends for frontends**.
- **Managed gateways** from cloud providers.
- **Gateway overreach**: the trap of putting too much in it.

## Many services, one door

As systems grow, they're often split into several **services**: orders, accounts, search, payments, each owned by a different team. Without anything in front, every outside client has to know where each service lives, and every service has to do the same chores itself:

- check the caller's API key or token,
- count requests and enforce rate limits,
- write access logs,
- set CORS headers,
- produce errors in a consistent format.

Twelve services means twelve versions of each chore, slowly drifting apart. One will eventually forget to check keys at all. A real security review found exactly that, which is Client B's story in the task.

An **API gateway** is a single entry point in front of all the services that does those shared jobs **once**, the same way, for every request. Step through it:

## What a gateway does

| Job | Example |
| --- | --- |
| **Authentication** | Check the API key or token. A bad one gets 401 at the door |
| **Rate limiting** | Count each client's requests. Over the limit gets 429, and no service is bothered |
| **Routing** | `/orders/...` to the orders service, `/accounts/...` to the accounts service |
| **Logging and analytics** | One place to see every request, per client |
| **TLS termination and CORS** | Handled once, at the edge |
| **Versioning** | Send `/v1/` and `/v2/` traffic to different versions of a service |
| **Shaping requests** | Add or remove headers, or adapt formats for older clients |

These are called **cross-cutting** jobs: every service needs them, and none of them is any service's real purpose. In the task you'll write the core of a gateway: check the key, count, route.

<details>
<summary>Quick check: a request has a stolen, invalid key. Which part should refuse it: the gateway or the orders service?</summary>

The gateway, with a 401, before the request reaches any service. That's one of its main jobs.
</details>

## Gateway, reverse proxy, load balancer

These overlap, and products often do all three, but the ideas differ:

| | Main job |
| --- | --- |
| **Load balancer** | Share requests between identical copies of one service |
| **Reverse proxy** | One public front that routes to different apps, and handles HTTPS |
| **API gateway** | A reverse proxy that also understands **API clients**: their keys, limits, usage and versions |

A real system might have all three: a gateway at the edge, routing to services, each of which runs several copies behind a load balancer.

## Backends for frontends

Sometimes the mobile app and the website need quite different data from the same services. One popular pattern puts a small, separate backend behind the gateway for each kind of client, a **backend for frontend** (BFF). The mobile BFF gathers exactly what each mobile screen needs from several services and returns it in one answer. It solves the same "too many requests per screen" problem as GraphQL, in a different way. Some teams use GraphQL as their BFF.

## Managed gateways

You rarely build a gateway from scratch. Common choices:

- **Amazon API Gateway** and **Azure API Management**, managed by the cloud providers,
- **Google Apigee**, popular with large enterprises,
- **Kong**, open source and also sold as a managed service.

They come with dashboards for keys, plans and usage, and often a developer portal where partners can sign up and read the docs. These are useful if the client sells API access.

## The trap: gateway overreach

Because every request passes through the gateway, it's tempting to put more and more into it: "while we're here, let's validate orders, calculate discounts, reshape this data for the iPhone app…". Resist that. A gateway full of business logic becomes:

- a **bottleneck** for change: every team must edit and redeploy the shared gateway,
- a **single point of failure** for everything, as from *Load balancers*,
- the place where logic is split confusingly between gateway and services.

Keep the gateway **thin**: cross-cutting jobs only. Business rules belong in the services. And run more than one copy, because if the front door is down, everything is.

<ConsultantNote>
Gateway products are often sold hard, and many small clients don't need one: a single backend can check its own keys. The signal that a client does need one is many services with duplicated, inconsistent auth, limits and logging. When you recommend one, also recommend the rule that keeps it healthy: "the gateway does auth, limits, routing and logging, and nothing else". Write it down, because that rule erodes quietly over time.
</ConsultantNote>
