## In this lesson

The webhooks lesson said "save the event, answer fast, and do the slow work afterwards". This lesson is about **afterwards**:

- **Doing work now or later**: what has to happen while a user waits, and what doesn't.
- **Message queues**, **producers** and **workers**.
- **Acknowledgements** and the **visibility timeout**: what happens when a worker crashes.
- **At-least-once delivery**: why a message can be processed twice.
- **Poison messages** and the **dead-letter queue**.

## Now, or a moment later?

When a customer places an order, a shop might need to save it, charge the card, email a receipt, generate a PDF invoice, update stock and notify the warehouse. If all of that happens **during** the request, **synchronously**, the customer stares at a spinner, and if any one step fails (the email service is down), the whole order fails.

But the customer only needs two of those things before seeing "Thank you": the order saved, and the card charged. Everything else can happen a moment later, **asynchronously**, in the background. The trick is handing that work off **safely**, so none of it is lost.

## Message queues

A **message queue** is a service that holds **messages**, each one a small piece of JSON describing a job, until something is ready to deal with them. Step through it:

<Viz name="message-queue" />

- A **producer** puts messages on the queue: the web server, saying "send a receipt for order 501".
- A **worker** (also called a **consumer**) is a separate program that takes messages off and does the work.

The two sides never talk directly, and they don't run at the same speed. That brings big benefits:

- **Fast answers**: the web server's part takes milliseconds.
- **Absorbing spikes**: a thousand orders in a minute just make the queue longer for a while, instead of overloading the email service.
- **Scaling**: emails piling up? Start more workers on the same queue. Each message goes to just one of them. That's horizontal scaling again.
- **Resilience**: if the email service is down, messages wait, and are retried, instead of failing customers' orders.

<details>
<summary>Quick check: in a queue setup, which part does the slow work, the producer or the worker?</summary>

The worker. The producer just adds a message describing the job, and carries on.
</details>

## Acknowledgements: done means done

Here's the subtle part. A worker takes a message and starts sending the email. Then the worker crashes. What happens to the message?

A good queue doesn't **delete** a message when a worker takes it. It **hides** it from other workers for a while, the **visibility timeout** (30 seconds in the practice API). Then:

- When the worker finishes, it sends an **acknowledgement** ("ack"): "done, delete it". Only now is it gone.
- If no ack arrives before the timeout, because the worker crashed or is stuck, the message becomes **visible again**, and another worker takes it.
- A worker can also give a message back on purpose, with a negative acknowledgement ("nack", or "release" in the practice API), when it knows it can't handle it right now.

So the rule for workers is: **acknowledge last**, only after the work is completely done. Acknowledge first and crash, and the job is silently lost.

## At least once, not exactly once

Follow that through and you'll spot a catch. A worker sends the email, and then crashes **before** acknowledging. The message reappears, and another worker sends the email **again**.

Most queues promise **at-least-once delivery**: every message will be processed, but occasionally **more than once**. Exactly-once is very hard to guarantee across networks, so the job falls to the worker: make the work safe to repeat (**idempotent**, from *Designing REST APIs*), or record which jobs are done and skip repeats, the same trick as skipping duplicate webhooks.

## Poison messages and the dead-letter queue

Some messages fail **every** time: an email address with a typo, a corrupt photo, a bug that crashes on one particular order. Retried forever, a **poison message** wastes workers, fills the logs, and can block the messages behind it.

So queues count how many times each message has been received. After a limit (3 in the practice API), they move it to a separate **dead-letter queue**: a holding area for messages that couldn't be processed. Nothing is lost, the rest of the work carries on, and a person, or an alert, can look at what went wrong. Stage 4 comes back to dead-letter queues when designing for failure.

## The practice queue

In the task you'll be both producer and worker, using the practice API's queue:

```python
address = BASE + "/queues/my-emails/messages/"

requests.post(address[:-1], json={"email": "ada@example.com"})   # add one (POST …/messages)

response = requests.get(address + "next")    # take the next one, or 204 if empty
message = response.json()                    # {"id": "m1", "body": {...}, "receive_count": 1}
requests.post(address + message["id"] + "/ack")       # done
requests.post(address + message["id"] + "/release")  # failed, put it back
```

(`address[:-1]` is the address without its last character, the slash, using the slicing from the debugging lesson.)

Your worker loops with `while` until `next` answers **204**, meaning nothing is waiting. Bad messages are released, come straight back, and after three tries the queue moves them to the dead-letter queue, so your loop ends by itself.

## Real queue products

You'd rarely write a queue yourself. Common choices:

| Product | Notes |
| --- | --- |
| **Amazon SQS** | Fully managed by AWS, simple, pay per message |
| **Azure Service Bus** | Microsoft's managed queues, popular with .NET teams |
| **RabbitMQ** | Open source, very flexible, you run it yourself (or pay a host) |
| **Redis-based queues** | Lightweight, popular with Node and Python apps, like BullMQ and Celery |

They all share the ideas in this lesson: producers, workers, acknowledgements, visibility or redelivery, and dead-letter queues.

<ConsultantNote>
"The checkout is slow" and "sometimes orders fail when the email service is down" are classic symptoms of doing everything synchronously. Moving the non-essential work onto a queue fixes both, and it's often a modest change. When you review one, ask: what happens if a worker crashes halfway? Is the work safe to repeat? Where do failed messages go, and does anyone get told?
</ConsultantNote>
