## In this lesson

This is the **Stage 2 milestone**: connect two services in a small app with live updates. Everything you need, you've already met. Here it all comes together:

- **Two services**: an orders service and a live order board, each a small Node program.
- The orders service tells the board about each new order with an **HTTP POST**, webhook-style. You'll write that part.
- The board pushes each order to the browser with **server-sent events**, so it appears without refreshing.
- Then you'll **explain** the design, as you would for a client or a colleague.

## What you're building

```text
 curl (a customer)            orders service             board service              browser
       │   POST /orders          (port 4396)               (port 4397)
       │ ───────────────────▶   saves an id     POST /events      │
       │                        notifyBoard()  ───────────────▶   writes to every   ───▶  the order
       │   ◀── 201 + order                                         open /stream            appears
```

1. A "customer" (you, with curl) sends `POST /orders` to the **orders service**.
2. The orders service gives the order an id and calls **`notifyBoard`**, which sends `POST /events` to the **board service** with an `order.created` event. **This is the function you'll finish.**
3. The board writes the event to a log file, and to every browser that has the board page open, through a **server-sent events** stream.
4. The page's JavaScript adds the order to the list.

Two separate programs, on two ports, talking over HTTP: a miniature version of the systems you've been learning about all stage.

## The starter files

Real projects rarely start from an empty folder. You'll download two starter files from Groundwork's practice API, the way a team would hand you a repository: `orders.js` and `board.js`. Read them before running them, because reading code you didn't write is half the job. Here are the parts that are new.

### Reading a form in the orders service

```javascript
const form = new URLSearchParams(body);   // body is "item=Desk lamp&customer=Ada"
form.get("item")                          // "Desk lamp"
```

`curl -d "item=…&customer=…"` sends form fields, as in the cookies lesson. **`URLSearchParams`** is built into Node and browsers. It reads that `name=value&name=value` text, and `.get()` picks out one field.

### The board's stream

```javascript
res.writeHead(200, { "Content-Type": "text/event-stream", "Cache-Control": "no-cache" });
res.write(": connected\n\n");
watchers.push(res);
```

This is a **server-sent events** endpoint, which you met in *Live updates*. It answers with the special content type `text/event-stream`, and then **never calls `res.end()`**: the response stays open. The board keeps each open response in the `watchers` array. When an event arrives, it writes to each one:

```javascript
watcher.write("data: " + body + "\n\n");
```

That's the whole SSE format: a line starting `data: `, then a **blank line** to mark the end of the message. (A line starting with a colon, like `: connected`, is a comment the browser ignores.)

### The board's page

```javascript
const events = new EventSource("/stream");
events.onmessage = (message) => {
  const order = JSON.parse(message.data).order;
  // … add it to the list …
};
```

In the browser, **`EventSource`** opens the stream and calls `onmessage` for every event, with the text after `data:` in `message.data`. If the connection drops, it reconnects by itself.

<details>
<summary>Quick check: why does the board never call res.end() on a /stream request?</summary>

Because the response has to stay open, so the board can keep writing new events to it. Ending it would close the stream.
</details>

## Your part: notifyBoard

In `orders.js`, this function is empty:

```javascript
async function notifyBoard(order) {
  // TODO: send a POST request to BOARD_EVENTS with fetch().
}
```

You've used `fetch` to **get** things, in *JavaScript outside the browser*. It can also send a POST, by giving it a second argument, an object of **options**:

```javascript
await fetch(url, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(data),
});
```

- **`method`**: which HTTP method. Without it, fetch sends GET.
- **`headers`**: an object of request headers. Here, saying the body is JSON.
- **`body`**: what to send, as text. `JSON.stringify` turns a JavaScript object into JSON text.

### When the board is down: try and catch

What if the board isn't running? `fetch` can't connect and **throws an error**. Unhandled, that would crash the orders service, and no one could place an order because a display screen was off. That's the wrong way round.

JavaScript's **`try`** and **`catch`** work like Python's `try` and `except`:

```javascript
try {
  // code that might fail
} catch (error) {
  console.log("Couldn't reach the board:", error.message);
}
```

If anything inside `try` throws, the code jumps to `catch`, with the error in `error`, instead of crashing.

So the finished function is:

```javascript
async function notifyBoard(order) {
  try {
    await fetch(BOARD_EVENTS, {
      method: "POST",
      headers: { "Content-Type": "application/json" },
      body: JSON.stringify({ type: "order.created", order: order }),
    });
  } catch (error) {
    console.log("Couldn't reach the board:", error.message);
  }
}
```

## Running it

You'll use three PowerShell windows:

| Window | Runs | Why |
| --- | --- | --- |
| 1 | `node board.js` | The board service, on port 4397 |
| 2 | `node orders.js` | The orders service, on port 4396 |
| 3 | curl commands | Plays the customer placing orders |

Plus a browser tab on `http://localhost:4397`, the board page. Arrange them so you can see the browser while you run curl, because that moment, when an order appears on its own, is the point of the exercise.

If something doesn't work, use the troubleshooting habits from this stage:

- **"Connection refused"** from curl: is the service on that port running, in its window?
- **The order is created (`order-1.txt` exists) but nothing appears**: look at window 2. Does it say "Couldn't reach the board"? Then check `notifyBoard` and the board's window. Did you save `orders.js`, and restart `node orders.js` after changing it?
- **The page says "Connecting..."**: is the board running? Refresh the page.

## Stepping back

You've built, in miniature, the shape of a lot of real software:

- **Two services** with one job each, talking over **HTTP**.
- A **webhook-style event** from one service to another.
- **Server-sent events** for live updates in the browser.
- **Error handling**, so one part failing doesn't take down another.

And you can already see what a real version would need, from the rest of this stage: orders saved in a **database**, a **queue** between the services so events aren't lost while the board is down, a **signature** on events, **HTTPS**, and perhaps an **API gateway** in front if it grew. Being able to look at a working system and name its next weaknesses is exactly what a consultant does.
