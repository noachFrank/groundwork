## The problem Git solves

You've probably seen folders like this:

```text
report.docx
report-final.docx
report-final-v2.docx
report-final-v2-REALLY-final.docx
```

Now imagine that with hundreds of files and five people editing at once. That's why nearly every software team in the world uses **Git**. It keeps every version of every file, records who changed what and why, and lets people work on the same project without overwriting each other.

## Three words to know

- **Repository** (or repo): a project folder that Git tracks. The history lives in a hidden `.git` folder inside it.
- **Commit**: a saved snapshot of the project, with a short message saying what changed. Like a save point in a game.
- **Staging**: choosing which changes go into the next commit.

## The routine

```text
edit files  →  git status  →  git add  →  git commit -m "what changed"
```

Why the extra `add` step? Because you often change several things at once, but they're different pieces of work. Staging lets you commit them separately, so each commit tells one clear story.

## Good commit messages

Your future self, and your teammates, will read these. Write what the change does, in a few words:

| Not helpful | Helpful |
| --- | --- |
| `stuff` | `Add a contact form` |
| `fix` | `Fix prices showing without tax` |
| `changes` | `Rename the title on the homepage` |

## Git and GitHub aren't the same thing

**Git** is the program on your computer that tracks history. **GitHub** is a website that stores Git repositories online so people can share them, like Google Drive for code. You can use Git without GitHub, which is what you'll do for most of this module, and you'll connect to GitHub at the end.

<ConsultantNote>
Git history is a goldmine when you're new to a client's project. `git log` shows who works on what, how often things change, and when problems started. Clients with no version control at all, still emailing zip files around, are common, and getting them onto Git is valuable work.
</ConsultantNote>
