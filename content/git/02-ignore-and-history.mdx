## In this lesson

- Why some files must **never** go into Git, and how `.gitignore` keeps them out.
- Why a secret committed once is a secret leaked forever.
- How to read a project's history: who changed what, when, and why.
- A first look at **CSS**, the language that styles web pages.

## Not everything belongs in Git

Git is meant for the files **people write**. Some files in a project folder shouldn't be tracked at all:

| Never commit | Why |
| --- | --- |
| `.env` and other secret files | Anyone with the code would get the keys (from *Environment variables and PATH*) |
| `node_modules/`, `.venv/` | Huge, and rebuilt from package.json or requirements.txt (from *Packages*) |
| `dist/`, `build/` | Made by a build, not written by people |
| Personal settings and junk | Like an editor's settings folder, or Windows' `Thumbs.db` |

## .gitignore

A file called **`.gitignore`**, in the top folder of the repository, lists names and patterns Git should ignore. Git then acts as if those files don't exist: they won't show up in `git status`, and `git add .` won't stage them.

```text
.env
node_modules/
dist/
```

- Each line is a file or folder name.
- A name ending in `/` means a folder and everything in it.
- `*` works as a wildcard, as in Bash: `*.log` means every file ending in `.log`.
- Lines starting with `#` are comments.

The `.gitignore` file itself **is** committed, so everyone on the team shares the same rules.

Notice its name starts with a dot, like `.env` and `.git`. That's the Linux tradition for settings files, which you met in the Bash lesson.

<details>
<summary>Quick check: you add `.env` to .gitignore. Is .env deleted?</summary>

No. The file stays on your computer, exactly as it was. Git just stops noticing it, so it never gets committed.
</details>

<Callout kind="warn" title="Git never forgets">
Git keeps every version, so a secret committed once stays in the history **even after you delete the file**. Anyone who can see the repository can look at that old commit. If a password or key is ever committed, especially to GitHub, **change it immediately**. Automated programs scan public repositories for keys within minutes.
</Callout>

That's why `.gitignore` should be set up **before** the first commit that could include secrets. In the task, you'll create it before committing anything else.

## A little CSS

In the task you'll add a second file to your website: a **stylesheet**. Stylesheets are written in **CSS** (Cascading Style Sheets), the language that controls how a web page looks: colors, sizes, spacing and layout. HTML says what things **are**. CSS says how they **look**.

```css
h1 { color: teal; }
```

That's one CSS rule. Read it as: "for every `h1` heading, make the text color teal". The part before the braces picks what to style. Inside the braces, each setting is a name, a colon, a value, and a semicolon.

That's all the CSS you need for this module. You'll learn more in Stage 3.

## Reading history

The history is one of Git's most useful features, especially in someone else's project.

| Command | Shows |
| --- | --- |
| `git log --oneline` | Every commit, one per line, newest first |
| `git show HEAD~1` | What one particular commit changed |
| `git show --stat HEAD~1` | Just which files that commit changed, and how much |
| `git diff` | Changes you haven't committed yet |
| `git blame index.html` | Who last changed each line of a file, and in which commit |
| `git ls-files` | Every file Git is tracking |

### Naming a commit

Every commit has a unique ID: a long code of letters and numbers, usually shown shortened to its first seven characters, like `ca05569`. You'll see them at the start of each line in `git log --oneline`.

There's also a handy nickname: **`HEAD`** means "the latest commit, where I am now". `HEAD~1` means one commit before that, `HEAD~2` two before, and so on. You can use either an ID or a HEAD name in commands like `git show`.

<details>
<summary>Quick check: what does `git show HEAD~2` show?</summary>

What changed in the commit two before the latest one.
</details>

### When output fills the screen

Commands like `git log`, `git show` and `git blame` sometimes show more than fits on screen. Git then lets you scroll with the arrow keys or Space, and shows a `:` at the bottom. **Press Q to get back to the prompt.** Everyone gets stuck here once.

<ConsultantNote>
On a security review, one of the first checks is searching a client's Git history for secrets, not just the current code. Tools exist for exactly this. Finding a live database password in a commit from three years ago is depressingly common.
</ConsultantNote>
