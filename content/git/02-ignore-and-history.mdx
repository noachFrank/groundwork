## Not everything belongs in Git

Some files should **never** be committed:

| Never commit | Why |
| --- | --- |
| `.env` and other secrets | Anyone with the code would get the keys |
| `node_modules/`, `.venv/` | Huge, and rebuilt from package.json or requirements.txt |
| `dist/`, `build/` | Generated by the build, not written by people |
| Personal settings and junk | Like `.vscode/` settings or Windows' `Thumbs.db` |

A file called **`.gitignore`**, at the top of the project, lists them. Git then acts as if they don't exist. The `.gitignore` itself is committed, so the whole team shares it.

```text
# .gitignore
.env
node_modules/
dist/
```

<Callout kind="warn" title="Git never forgets">
Git keeps every version, which means a secret committed once stays in the history even after you delete it. If a password or key is ever committed, especially to GitHub, **change it immediately**. Bots scan public repositories for keys within minutes.
</Callout>

## Reading history

The history is one of Git's most useful features, especially in someone else's project.

| Command | Shows |
| --- | --- |
| `git log --oneline` | Every commit, one per line |
| `git show HEAD~1` | What a particular commit changed |
| `git diff` | Changes you haven't committed yet |
| `git blame file` | Who last changed each line, and in which commit |

`HEAD` means "the latest commit where I am". `HEAD~1` is one before that, `HEAD~2` two before, and so on. Every commit also has an ID, like `ca05569`, which you can use instead.

<ConsultantNote>
On a security review, one of the first checks is searching a client's Git history for secrets, not just the current code. Tools exist for exactly this. Finding a live database password in a commit from three years ago is depressingly common.
</ConsultantNote>
