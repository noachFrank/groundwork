## Parallel lines of work

A **branch** is a separate line of commits. While you work on a branch, `main` stays exactly as it was. When the work is ready, you **merge** it back.

## Why teams work this way

- **main always works.** Half-finished features never break the version people use.
- **Everyone works separately.** One person fixes a bug on one branch while another builds a feature on another.
- **Work can be checked before it joins.** That's what pull requests are for, coming up in a later lesson.
- **Experiments are cheap.** Try an idea on a branch. If it doesn't work out, delete the branch.

## The commands

| Command | What it does |
| --- | --- |
| `git switch -c name` | Make a new branch and switch to it |
| `git switch name` | Switch to an existing branch |
| `git branch` | List branches. The one marked `*` is where you are |
| `git merge name` | Bring `name`'s commits into the branch you're on |
| `git branch -d name` | Delete a branch that's been merged |

Older tutorials and AI answers often use `git checkout` for switching branches. It still works. `git switch` is newer and harder to misuse.

## Two kinds of merge

- **Fast-forward.** If main hasn't changed since the branch started, Git just moves main forward to include the branch's commits. No extra commit.
- **Merge commit.** If both have new commits, as in the task, Git combines them and records a special commit with two parents. That's the `Merge branch 'add-about'` line in your graph.

Either way, you usually don't have to think about it. Git sorts it out, unless the same lines were changed on both sides. That's a **conflict**, and it's the next lesson.

<ConsultantNote>
How a team uses branches says a lot about how it works. Does main always work? Is work reviewed before merging? Can anyone push straight to main? Simple rules here prevent a lot of "who broke the site?" moments, and setting them up is a quick win for a client.
</ConsultantNote>
