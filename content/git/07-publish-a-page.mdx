## In this lesson

The Stage 1 milestone. You'll put a page on the public internet, with an address you can send to anyone.

- Use AI to help write a small web page, the right way.
- Push it to **GitHub**.
- Publish it, free, with **GitHub Pages**.
- Understand what a **deployment** and a **static site** are.

It pulls together everything from Stage 1: the terminal, Git, and using AI well. This lesson needs the internet throughout.

## How it fits together

```text
your laptop                GitHub                       the world
my-site/index.html  ──push──▶  my-first-site repo  ──Pages──▶  https://you.github.io/my-first-site/
```

1. **Git** tracks your page's versions on your laptop, as it has all module.
2. **Pushing** copies those commits to a repository on **GitHub**: a remote, exactly like the practice shared copy from the remotes lesson, except it's on the internet.
3. **GitHub Pages**, a free GitHub feature, takes the files in that repository and serves them as a website, at a public address.

Every time you push a change, Pages republishes the site, usually within a minute or two. Putting a new version of software where people use it is called a **deployment**, and plenty of professional hosting works exactly this way: push, and it goes live.

## GitHub accounts and repositories

You'll make a free GitHub account, then a new, empty repository on GitHub's website. Each repository on GitHub has an address like:

```text
https://github.com/YOUR-USERNAME/my-first-site.git
```

Your `my-site` repository already has a remote called `origin`: the practice shared copy from the remotes lesson. A repository can have several remotes, each with its own name, so you'll add GitHub as a second remote called `github`:

```text
git remote add github https://github.com/YOUR-USERNAME/my-first-site.git
git push -u github main
```

## Signing in from Git

GitHub doesn't accept your account password from the terminal. Instead, Git for Windows includes **Git Credential Manager**, which opens a browser window to sign in securely the first time you push. After that, it remembers you on this computer.

## Using AI for this, the right way

It's fine, and realistic, to have AI help write the page. But it's *your* page, with your name on it. Use the routine from the first lesson of the course:

- **Ask for something simple:** a single HTML file about you and what you're learning, using only HTML and CSS.
- **Read the code** before you publish it. You know `<h1>`, `<p>`, `<a>` and basic CSS rules now. Ask the AI about every tag or rule you don't recognize, until you could explain the whole page.
- **Change something yourself**: the colors, a heading, a section.
- **Check what's in it.** AI sometimes adds links to outside scripts, fonts or images you didn't ask for. For this page, it should be one HTML file that doesn't load anything from elsewhere.

<Callout kind="warn" title="Your page is public">
Anyone in the world can open it, and search engines may find it. Don't put your address, phone number, or anything else private on it. Remember *Asking good questions*: private data stays private.
</Callout>

## Opening a file from the terminal

`start index.html` opens a file with whatever program normally opens that kind of file, as if you'd double-clicked it. For an `.html` file, that's your browser. It's a quick way to check the page looks right before you commit it.

## Static sites

Your page is a **static site**: a set of files that are sent to the browser exactly as they are. There's no server program running code for each visitor, and no database.

| Static site | Site with a backend |
| --- | --- |
| Just files: HTML, CSS, images | Files, plus a server program and usually a database |
| Free or very cheap to host | Costs money to run all the time |
| Very fast | Slower, because it does work for each request |
| Little to attack, so hard to hack | More to secure |
| Can't do logins, saved data or payments by itself | Can do anything |

Many real business websites are static. When a site needs logins, a database or payments, it needs a backend too. That's Stage 3.

<details>
<summary>Quick check: a bakery wants a website with its opening hours, menu and a map. Does it need a backend?</summary>

No. That's all information that rarely changes, so a static site is enough, and much cheaper and safer.
</details>

<ConsultantNote>
"Do we really need a server for this?" is a question that saves clients money. Many small business sites would be faster, safer and nearly free as static sites. Recognizing when the simple option is enough is good consulting.
</ConsultantNote>
